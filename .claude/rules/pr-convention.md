# PR 규칙

템플릿은 `.github/pull_request_template.md`에 있고 GitHub이 새 PR 본문에 자동으로 채운다.
본문을 자동으로 채우려면 `/pr-summary` 스킬을 쓴다.

## 0. 판단 기준 하나

> **PR 본문은 diff를 다시 쓰는 곳이 아니다.** diff는 코드가 이미 말한다.

여기 쓸 것은 두 가지다: **왜 이렇게 했는지**와 **어디를 봐야 하는지**.

```
❌ apps/shell·goals·investments를 apps/web으로 합치고 next.config.js에 rewrites를 추가했습니다.
   packages/tokens와 packages/core를 새로 만들었습니다.

✅ nextjs-mf 공식 문서에 App Router 미지원과 지원 종료가 명시돼 있어 스트리밍 SSR과 MFE를
   동시에 가질 방법이 없었다. 조립 지점을 런타임 번들에서 요청 라우팅으로 옮겨 두 요구가
   서로를 막지 않게 했다. 근거는 ADR-001.
```

## 1. 필수 섹션

| 섹션 | 왜 필요한가 |
|------|------------|
| **무엇을 · 왜** | 6개월 뒤 "이건 왜 이렇게 했나"에 답하는 유일한 기록. 2~4줄 |
| **영향 범위** | 이 레포는 영역 4개(`pm`·`salt-microFe`·`bff`·`salt-server`)다. 어디가 움직였는지가 리뷰어를 정한다 |
| **REQ 번호 + 스펙·체크리스트 링크** | 근거 추적이 여기에 의존한다 |
| **리뷰 초점** | 리뷰어가 어디를 볼지 모르면 파일 순서대로 훑는다. 그러면 중요한 판단이 묻힌다 |
| **검증** | 돌린 것만 체크한다. 안 돌린 것을 체크하면 이 섹션 전체가 무의미해진다 |
| **미검증 · 범위 밖** | **빈칸으로 두지 않는다.** 없으면 "없음"이라고 쓴다 |
| **머지 전 남은 것** | 작성자가 할 일. 리뷰어 요청이 아니다 |

## 2. "미검증 · 범위 밖"을 반드시 채운다

이 규칙의 핵심이다. **못 한 것을 적는 칸이 없으면 사람은 적지 않고, 리뷰어는 다 됐다고
읽는다.** 그 오해가 릴리스까지 가면 사용자 머신에서 처음 드러난다.

각 항목에 **사유**와 **언제 닫히는지**를 함께 쓴다:

```markdown
| 항목 | 사유 | 언제 닫히나 |
|------|------|------------|
| `/coach`·`/assets` soft navigation 실측 | 두 경로가 아직 없다 | F006 (`FE-REQ-030`~`033`) |
| 관측성 계측 | 배포 인프라가 없어 보낼 곳이 안 정해졌다 | 배포 환경 확정 시 |
```

"언제 닫히나"가 비면 그건 미검증이 아니라 **잊힌 것**이다.

**체크리스트 리포트가 진실이다.** `<area>/requirements/reports/checklists/<REQ-ID>.md`의
미충족 항목과 이 표가 어긋나면 안 된다. 둘 중 하나가 거짓이라는 뜻이다.

## 3. 리뷰 초점 — 파일이 아니라 판단을 적는다

```
❌ salt-microFe/apps/** 를 봐주세요
✅ 1. 배포 대상을 자체 호스팅(FR-21)으로 정한 판단 — Vercel Public Beta에 배포 구조를 묶지 않는다
   2. zone을 세금 하나만 자른 경계 (탭으로 자르면 가장 잦은 이동이 full reload가 된다)
   3. lint 규칙의 zone 경로가 레지스트리와 두 곳에 있는 절충 (CommonJS 제약)
```

판단이 필요한 지점이 없으면 **"없음 — 스펙 그대로"** 라고 쓴다. 그것도 정보다.

## 4. 커밋을 나눈 이유를 적는다

커밋이 두 개 이상이면 **왜 나눴는지** 한 줄씩 적는다. 구조 변경과 그 위의 구현이
한 커밋에 섞이면 리뷰어가 둘 중 하나를 못 본다.

```markdown
- `5a0276c` feat(fe) — 3앱 → zone 2개 통합. 초점은 "합쳐도 잃는 게 없나"다
- `d425cbe` feat(fe)! — nextjs-mf 제거. **되돌리려면 이 커밋 하나만 revert한다**
```

**되돌리기 비용이 큰 변경은 단일 커밋으로 가둔다.** 그러면 revert 지점이 하나가 된다.

## 5. 계약 변경은 눈에 띄게

리뷰어가 놓치면 다른 사람 작업이 조용히 깨지는 것들이다.

- **`.claude/rules/` 변경** — 어떤 규칙이 왜 바뀌었는지. 규칙은 모든 후속 작업의 전제다
- **BREAKING** — 소비처가 고쳐야 하는 것을 구체적으로. `feat!`/`refactor!` 커밋 접미사와 짝
- **ADR** — 되돌리기 비용이 큰 결정은 `requirements/decisions/ADR-*.md`에 남긴다
- **BFF ↔ 프론트, 서버 ↔ BFF 계약** — 한쪽만 바꾸면 다른 쪽이 조용히 깨진다
- **Prisma 마이그레이션** — 롤백 가능한가

## 6. 제품 공통 수용 기준

`requirements/specs/in-progress/salt-requirements-master-index.md` §6의 항목은 **기능과
무관하게** 모든 PR에 걸린다. 특히 이 넷은 법적 포지셔닝(글로벌 플랜 §1)에서 나온 것이라
타협 대상이 아니다.

1. 추천에 **근거 · 과거 적중률 · 실패사례** 3종이 전부 붙는다. 하나라도 없으면 렌더하지 않는다
2. **주문을 실행하는 코드 경로가 없다**
3. 금액 계산은 **서버에서** 한다. 프론트는 표시만, LLM은 문장만
4. 확신 표현과 목표주가·수익률 예측이 0건이다

## 7. 크기

- 기본은 **REQ 하나**다. 여러 REQ를 묶었으면 **왜 묶었는지**를 본문에 적는다
- 영역(`salt-microFe`·`bff`·`salt-server`)을 넘는 PR은 **계약 변경이 있을 때만** 정당하다.
  그 외에는 영역별로 나눈다
- 파일 수가 많은 것 자체는 문제가 아니다 — 기계적 rename은 100개도 리뷰된다.
  문제는 **판단이 여러 개 섞이는 것**이다. 그때는 커밋으로 나눈다
- 아키텍처 변경은 **항상 별도 커밋**으로 분리한다

## 8. 하지 않는 것

- ❌ 스크린샷만 붙이고 본문을 비우기 — 왜가 없으면 6개월 뒤 아무것도 안 남는다
- ❌ 스펙 내용을 PR에 복사 — 링크한다. 두 곳에 있으면 갈라진다
- ❌ 안 돌린 검증을 체크
- ❌ "미검증: 없음"인데 실제로는 확인하지 않은 것 — 체크리스트 리포트와 일치해야 한다
- ❌ 체크리스트·회고 없이 REQ를 `done/`으로 옮기기
- ❌ `main`에 직접 push
