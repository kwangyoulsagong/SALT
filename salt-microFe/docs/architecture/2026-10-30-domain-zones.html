SALT 프론트엔드 도메인 아키텍처

SALT를 투자 앱이 아니라 돈 관리 앱으로 다시 세운다. 마이크로프론트엔드의 경계를 도메인으로 긋는다. 셸 하나와 도메인 zone 넷(투자 · 저축 · 가계부 · 금융 팁)이 각자 독립 Next 앱으로 배포되고, 경계는 규칙과 lint가 강제한다.

결론

  1. zone = 도메인. apps/web(셸) · apps/web-investment · apps/web-savings · apps/web-household · apps/web-tips. 각자 빌드 · 배포 · 롤백한다. apps/web-tax는 지운다.
  2. 셸은 도메인을 모른다. 로그인 · 온보딩 · 홈 · 공용 크롬(하단 탭 · 헤더)만 갖는다. 홈은 도메인마다 요약 카드 한 장을 BFF에서 받는다.
  3. 화면 코드는 도메인 패키지에. packages/domain-* 안이 FSD다. zone 앱은 라우트 · 레이아웃 · 설정만 갖는 얇은 조립 층이다.
  4. 규칙을 바꾼다. 지금 microfrontend.md §2(세 조건 + "탭으로 자르지 않는다")를 "도메인으로 자른다"로 개정한다. 대가인 zone 간 새로고침은 미리 렌더 · 문서 간 전환으로 줄인다.

zone 앱에 화면 코드를 두지 않는 이유: 각 zone은 따로 배포되지만 같은 디자인 시스템과 크롬을 써야 한 앱처럼 보인다. 화면 코드가 패키지에 있으면 Storybook · 테스트 · 모바일 웹뷰가 같은 코드를 쓰고, zone을 합치거나 다시 나누는 일이 설정 수준으로 끝난다.

규칙 개정안 — microfrontend.md

지금 규칙은 "세 조건을 모두 만족해야 zone"이고 "탭으로 자르지 않는다"다. 이걸 아래로 바꾼다. 규칙 표는 문서가 아니라 코드(@repo/core/zones · layer-rules.cjs)가 진실이라는 기존 원칙은 그대로다.

§1 zone 경계

zone 하나 = 도메인 하나. 도메인 목록은 @repo/core/zones 레지스트리 한 곳이고, 서버 서비스 · BFF 라우트 · 모바일 서비스 번들 이름과 같다. 새 도메인은 레지스트리에 먼저 추가한다.

§2 셸의 책임

셸은 인증 · 온보딩 · 홈 · 공용 크롬만 갖는다. 셸은 어떤 domain-* 패키지도 import하지 않는다. 홈의 도메인 정보는 HomeSummaryCard[]로만 받는다.

§3 도메인 격리

domain-* 패키지끼리 import 금지. 도메인 사이의 연결은 URL 링크와 BFF 응답(서버가 계산한 값)으로만 한다. 예: 가계부의 "이 지출이 목표를 며칠 늦추나"는 household 응답에 서버가 넣는다.

§4 zone 앱은 얇다

apps/web-*는 app/ 라우트 · 레이아웃 · next.config.js만 갖는다. src/에 entities · features · widgets를 만들지 않는다.

§5 zone 간 링크

다른 zone 경로는 CrossZoneLink(<a> + 로딩 상태 + 미리 렌더 힌트). next/link는 같은 zone 안에서만. lint가 레지스트리를 읽어 강제한다.

§6 공용 크롬 · 버전

하단 탭 · 헤더는 @repo/ui의 AppChrome 하나. 공용 패키지가 바뀌면 영향받는 zone을 같이 배포한다(turbo 영향 그래프로 판정). zone을 넘는 기능은 기능 플래그로 동시에 켠다.

§7 경로 · 자산

경로 prefix와 assetPrefix(/{zone}-static)는 zone 간 유일하다. 셸 rewrites는 레지스트리에서 생성한다(손으로 쓰지 않는다).

강제 위치무엇을
packages/eslint-plugin-fsd/layer-rules.cjs§2 · §3 · §4 — 도메인 축(domain-* ↔ domain-*, 셸 → domain-*) 추가. 쓰기 시점 훅도 같은 표를 읽는다
packages/eslint-plugin-zone§5 — 대상 경로를 /tax에서 레지스트리 전체로
packages/core/src/zones/registry.ts§1 · §7 — zone 5개 · 포트 · prefix · assetPrefix. 셸 next.config.js가 여기서 rewrites를 만든다

zone 이동 완화

zone을 넘는 이동은 문서 이동이다. 모든 zone이 같은 origin이라 자체 호스팅에서도 아래 장치를 쓸 수 있다. 하단 탭이 zone을 넘는 가장 잦은 이동이라 여기에 집중한다.

장치무엇을 하나한계
Speculation Rules (prerender)AppChrome이 하단 탭 링크에 <script type="speculationrules">를 건다. 마우스를 올리거나 누르기 시작할 때(eagerness: moderate) 해당 zone 첫 화면을 미리 렌더해서 누르면 바로 바뀐다Chromium 계열. Safari는 일반 이동
문서 간 View Transitions모든 zone CSS에 @view-transition { navigation: auto; }. 하단 탭 · 헤더에 같은 view-transition-name을 줘서 크롬은 제자리, 본문만 바뀐다같은 origin만(조건 충족)
서버 렌더 첫 화면각 zone 첫 화면의 핵심 숫자(시세 · 목표 진척 · 이번 달 지출)를 RSC 스트리밍으로 HTML에 넣는다. 클라이언트 캐시가 비어 있어도 숫자가 바로 보여 "가격 깜빡임 금지"를 지킨다—
공용 정적 자산 캐시React · 디자인 시스템 청크를 zone끼리 같은 해시로 내보내면 브라우저 캐시를 같이 쓴다(공용 패키지를 같은 버전으로 묶는 이유)zone별 번들러 설정이 같아야 한다

각 zone 안의 이동(예: /investments → /investments/[symbol] → /coach/report)은 같은 앱이라 지금처럼 부드럽다.

홈은 어떻게 도메인을 모으나

셸이 도메인 코드를 모르므로, 홈은 도메인마다 카드 한 장을 받는다. 카드 모양은 packages/core의 HomeSummaryCard 하나로 고정하고, BFF /api/app/home이 도메인 서비스를 병렬로 불러 채운다(allSettled — 한 도메인이 죽어도 홈은 뜬다).

type HomeSummaryCard = {
  domain: "invest" | "savings" | "household" | "tips";
  title: string;                               // "이번 달 지출"
  primary: { label: string; value: string };   // 서버가 포맷한 문자열 — FE 계산 0
  secondary?: { label: string; value: string };
  href: string;                                // 도메인 zone 진입 경로
  state: "ok" | "empty" | "degraded";
  updatedAt: string;
};

기본 순서는 저축 → 가계부 → 투자 → 팁이고 사용자가 바꾼다. 지금 home-briefing이 entities/coach · portfolio를 직접 읽는 것은 §2 위반이 되므로 F1에서 같이 끊는다.

하단 탭과 IA

  • 탭 4개: 홈 · 저축 · 가계부 · 투자. 금융 팁은 탭이 아니다. 홈 카드 · 각 도메인 안의 때맞춘 팁으로 들어오고, 공개 URL /tips는 검색으로 들어온다.
  • "탭을 줄인다"는 기존 방향(2026-09-09)에 맞춰 5개를 넘기지 않는다.
  • 데스크톱은 왼쪽 내비 4항목. FE-REQ-047(헤더 · 패널 위계)과 같이 조정한다.

모바일(RN) — 바뀌는 것

RN 앱은 아직 코드가 없다(apps/mobile 없음). 요구사항 23건(RN-REQ-001~031)이 전부 to-do다. 코드 변경은 없지만, 이번 설계와 어긋나는 문서가 있어 착수 전에 고쳐야 한다.

문서지금바꿀 것
RN-REQ-002 모바일 MFE서비스 번들 경계 coach · assets · tax · plan(ADR-001 §4)invest · savings · household · tips + 셸. 웹 zone과 같은 이름. tax 삭제. "OTA로 시작, 번들 분리는 조건이 생길 때"는 유지
RN-REQ-001 앱 구조 · 웹뷰 계약네이티브 + 정보 많은 화면은 웹뷰, UA SALTApp/어느 zone을 웹뷰로 쓸지 정한다. 안: 금융 팁 · 투자 상세 · 코치 리포트 = 웹뷰, 홈 · 가계부 입력 · 저축 = 네이티브(입력 속도 · 위젯)

RN에서만 생기는 것

  • 가계부 입력이 네이티브여야 하는 이유: 3초 입력(금액 먼저 숫자 키패드), 결제 문자를 공유 시트로 앱에 보내기(Android 공유 인텐트 · iOS 공유 확장 — 문자 읽기 권한이 아니라 사용자가 보내는 것).
  • 홈 화면 위젯: 저축 "모이는 장면" 위젯(기획서 재미 항목). iOS WidgetKit · Android 앱 위젯은 네이티브 모듈이 필요하다.
  • 웹뷰가 되는 zone은 휴대폰 폭이 필요하다: 지금 웹은 768px 미만에서 안내 한 장으로 덮는다(FE-REQ-043). 웹뷰로 쓰는 zone과, 공개 검색 유입을 받는 apps/web-tips는 이 규칙에서 빼고 휴대폰 폭 레이아웃 REQ를 따로 만든다.
