# 규칙 후보 — 금융 입력 검증: "고칠 수 있게 알려 주기"

> **상태: 후보(아직 적용 안 함).** `.claude/rules/**` 에 넣기 전 보관본이다. 도입할 때 "새로 넣을 것"을 새 규칙 파일
> (`form-validation.md` — 레지스트리 인덱스 `CLAUDE.md` 에 한 줄)로 옮기고 이 파일 머리에 날짜를 적는다.
>
> 출처: Roman Fedytskyi, *Why Frontend Validation Matters in Fintech*, Medium, 2026-10-05
> (https://medium.com/@roman_fedyskyi/why-frontend-validation-matters-in-fintech-377f09d5a988). 원문 번역이 아니라 우리 규칙 모양으로 요약했다.
> 글의 예시는 달러 · 소수 둘째 자리다 — 우리는 **원(소수 없음)** · 코인 수량(소수 8자리) · 국내 주식 수량(정수)이라 숫자는 바꿔 읽는다.

## 한 문장

> 프런트 검증은 **사람이 뜻한 금액 · 계좌 · 날짜를 넣고, 틀리면 추측 없이 고치게** 하는 일이다. 막는 일이 아니고(서버가 다시 본다), 오류 문구는 금융 경험의 일부다.

글의 첫 장면: `12,50` 을 넣자 빨간 테두리만 뜨고, 쉼표를 지우니 경고가 사라져 값이 `1250` 이 됐다 — **받아들였지만 무엇을 받았는지 설명하지 못한 폼**.

## 1. 이미 우리 규칙에 있는 것

| 글의 권고 | 우리 규칙 |
|---|---|
| 서버가 모든 중요한 검사를 다시 한다 · 클라이언트 검사는 우회된다 | 제품 공통 기준 3(금액 계산은 서버) · 서버 Zod DTO(`salt-server/.claude/rules/api-contract.md`) |
| 백엔드 예외 원문을 보이지 않고 코드 → 문구로 | `api-convention.md`(`ApiError.code` 로 문구 고름, 서버 `message` 안 읽음) |
| "검토" 와 "보내기" 를 나눈다 · 확인 표시가 송금 완료처럼 보이지 않게 | 주문 실행 경로 0(공통 기준 2) — 우리는 보내기 자체가 없다. 거래는 수동 기록 |
| 라벨 · 색만으로 상태 전달 금지 | `a11y-policy.md` |

## 2. 새로 넣을 것 (도입 후보)

| # | 규칙 | 우리 자리 |
|---|---|---|
| V1 | **편집 중 값은 문자열로 둔다** — `12.` 은 실수가 아니라 입력 중일 수 있다. 숫자 변환은 blur · 제출 때만, 고칠 때 원래 입력을 지우지 않는다 | 거래 기록 수량 · 단가 · 지출 금액 · 저축 적립 · 주문 전 체크 금액 |
| V2 | **조용히 반올림 · 기호 제거 금지** — 소수 자리 초과 · 쉼표 · 통화 기호는 고쳐서 받지 말고 이유를 말한다. 쉼표가 소수점인지 자릿수 구분인지 **추측하지 않는다**(지역 정책을 명시) | 원 금액(소수 없음) · 코인 수량 8자리 · 국내 주식 수량 정수 |
| V3 | 금액에 `Number()` 강제 변환(`z.coerce.number`) 대신 **명시 파서** — 형식 · 범위를 한 함수가 판단하고 결과는 최소 단위 문자열(원 · 사토시처럼). 지수 표기 · 음수 · 앞자리 0 정책을 파서에 | `@repo/core` 에 자산군별 파서 하나 — 화면마다 다시 적지 않는다(서버 DTO 와 같은 규칙인지 대조 테스트) |
| V4 | **오류 문구는 고치는 법** — "잘못된 금액" ✗ → "숫자만, 최대 8자리 소수" ✓. 한도 오류는 범위를, 원격 확인 실패는 다시 시도를 — **연결 문제를 "입력이 틀렸다"로 말하지 않는다** | 각 슬라이스 `model/messages.ts` |
| V5 | **검증 시점** — blur 와 제출 때 검사, 고치는 즉시 오래된 오류 · 검토 문구를 지운다(키 입력마다 값을 다시 쓰지 않는다) | 입력칸 공용 컴포넌트(`@repo/ui`) |
| V6 | 칸 접근성 — 보이는 라벨 · 예시(힌트) · 오류 문장을 `aria-describedby` 로 묶고 `aria-invalid`, 오류는 `aria-live="polite"`. 제출 실패 뒤 **첫 오류 칸으로 포커스**, 긴 폼은 오류 요약(칸 링크). 유일한 버튼을 비활성화해 무엇이 빠졌는지 못 찾게 하지 않는다 | `@repo/ui` 입력 · 폼 |
| V7 | `inputMode="decimal"` 은 키보드 힌트일 뿐 검증이 아니다 — 형식 검사는 그대로 | 금액 칸 |
| V8 | **식별자는 문자열** — 종목 코드(`005930`) · 계좌 · 코드형 값은 숫자로 바꾸지 않는다(앞자리 0) | 국내 종목 코드 · 초대 코드 |
| V9 | **관계 검사는 해당 칸에** — 두 칸 관계 오류(출금 = 입금 계좌 같은 것)는 고칠 칸 옆에. 단 관계 검사가 소유 · 권한을 증명하지 않는다 | 사람 장부 · 통장 쪼개기 · 목표 나눠 넣기 |
| V10 | **원격 확인 경합** — A 를 확인 중 B 로 바꾸면 A 의 늦은 성공이 B 옆에 뜨면 안 된다: 관련 칸이 바뀔 때 이전 결과를 버리고, 요청을 취소하고, 응답이 지금 입력판과 맞을 때만 적용 | 검색 · 계산기(서버 디바운스 계산 — 저축 목표 계산 · 주문 전 체크 미리보기) |
| V11 | 통화 · 자산군이 바뀌면 그 정밀도로 낸 결과를 무효로 · 기준(계좌 · 종목)이 바뀌면 그에 딸린 확인을 무효로 | 거래 기록(코인 ↔ 국내 전환) |
| V12 | **제출 시간 초과에 "다시 보내기"를 바로 권하지 않는다** — 상태 확인 흐름으로(중복 기록 방지). 서비스 실패는 칸이 아니라 폼 수준 문구 | 거래 기록 · 지출 · 적립(서버 멱등 키가 있어도 문구가 중복을 부르지 않게) |
| V13 | 브라우저 한도 힌트는 서버 정책과 같은 값(서버가 준 값) — 캐시된 한도는 제출 전에 바뀔 수 있다 | 추적 상한 10 · 입력 범위는 서버 값(`done-checklist.md` §2-2) |

## 3. 테스트 목록 (도입할 때 같이)

- 빈칸 · 0 · 음수 · 쉼표 · 점 두 개 · 지수(`1e3`) · 정확히 한도 · 한도 바로 밖 · 소수 자리 초과
- 고치는 흐름: 덜 끝난 소수(`12.`) · blur · 키보드 제출 · 오류 뒤 포커스 · 검토 뒤 고치기(검토 문구 지워짐)
- 관계 칸 오류 · 늦게 온 원격 응답(순서 뒤바뀜)
- DOM 시뮬레이션은 실기기 키보드 · 스크린리더를 대신하지 않는다 — 390 앱 웹뷰 · 실기기 1회(`done-checklist.md` §3-2)
