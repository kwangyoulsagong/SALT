## Summary

모바일 MFE의 값 중 **가장 큰 것("스토어 심사 없이 배포")은 번들을 쪼개지 않아도 OTA로 얻는다.** Phase 1은 `expo-updates`로 시작한다. **번들 분리(Re.Pack 5 + Module Federation 2)는 조건이 생길 때** 도입하고, 그 조건을 이 문서가 못 박는다.

## 모바일 MFE의 값은 웹과 다르다

| | 웹 | 모바일 |
|---|---|---|
| 해결하는 문제 | 한 도메인을 여러 배포로 쪼개기 | **스토어 심사를 우회해서 화면을 배포하기** |
| 배포 마찰 | 없음 (바로 나간다) | **심사 1~3일** |
| 채택 방식 | Multi-Zones (`ADR-001`) | OTA → (조건 시) 번들 분리 |

## 토스가 얻은 것 — 수치로 확인된 근거

[toss.tech, 2024](https://toss.tech/article/react-native-2024)

| 항목 | 내용 |
|---|---|
| 번들 분리 | **Shared Bundle**(`react-native` 등 네이티브 결합 코드, 전 서비스 공유) + **Service Bundle**(서비스별, 실행 시 필요한 것만 동적 로드) |
| 번들러 | Metro 대신 **ESBuild**. Metro는 빌드가 느리고 **tree-shaking을 지원하지 않고** 캐시를 리셋하지 않으면 일관성이 없다. ESBuild로 **빌드 1분 이내** |
| 배포 | 정적 JS 1개를 빌드·업로드 → 자체 어드민에서 **1초 배포**, CDN 경유 |
| 카나리 | **1~100% 임의 사용자 그룹** 부분 배포 |
| 성능 | 파일시스템에서 JS를 읽으므로 WebView의 네트워크 로딩이 사라진다. 실제 화면에서 **1초 이상 로딩 감축** |
| 추가 최적화 | **Hermes** 사전 컴파일로 초기 로딩 개선 |
| 복잡도 | SSR의 universal 코드(서버·클라이언트 양쪽 고려)가 없어지고 **클라이언트만** 고려한다 |

## 그런데 우리는 토스가 아니다

| | 토스 | SALT |
|---|---|---|
| RN 플랫폼 전담 | **4명** (FE 3 + iOS 1, 매일 짝 프로그래밍) | **0명** |
| 서비스(사일로) 수 | 다수, DRI 문화로 독립 배포가 조직 요구 | 기능 7개, 조직 하나 |
| 사용자 | 대규모 | **≤10명 (비공개·초대제)** |
| 자체 어드민·CDN·인프라 | 보유 | 없음 |
| RN 뷰 실행 빈도 | WebView보다 높다 | 앱이 아직 없다 |

**같은 것을 처음부터 만들면 그 자체가 제품보다 커진다.**

## 후보 5개를 비교했다

| | A. `expo-updates` OTA | B. Re.Pack 5 + MF 2 | C. CodePush | D. 토스형 자체 구축 | E. MFE 없음 |
|---|---|---|---|---|---|
| 스토어 심사 없이 배포 | **✓** | ✓ | ✓ | ✓ | ✗ |
| 기능 단위 배포 | ✗ 전체 번들 교체 | **✓** | ✗ 전체 | ✓ | ✗ |
| 필요할 때만 다운로드 | ✗ | **✓** | ✗ | ✓ | ✗ |
| 카나리·점진 롤아웃 | ✓ 채널·롤아웃 | 직접 구현 | ✓ | ✓ | ✗ |
| tree-shaking | Metro 기본 (약함) | **✓ Rspack** | Metro | ✓ ESBuild | Metro |
| Expo와 양립 | **✓ 기본 제공** | **✗ 공식 미지원** | 조건부 | ✗ | ✓ |
| 설정·운영 비용 | **가장 낮다** | 높다 | 중간 | **가장 높다** | 0 |
| 전담 인력 필요 | 0 | 1명 수준 | 0~1 | **4명 수준** | 0 |

### C를 버린 이유
Microsoft App Center가 은퇴했고 CodePush는 커뮤니티/자체 호스팅 경로로 남았다. **Expo를 쓰기로 한 이상(`RN-REQ-001`) `expo-updates`가 같은 값을 1급 지원으로 준다.** 굳이 다른 OTA를 얹을 이유가 없다.

### D를 버린 이유
토스가 만든 것을 우리가 만들면 **자체 어드민 + CDN + 카나리 인프라 + ESBuild 파이프라인**이다. 전담 4명이 한 일이고 우리는 0명이다. **이걸 만드는 동안 F001~F004가 멈춘다.**

### E를 버린 이유
스토어 심사 없이 배포하지 못하면 **세금 D-Day처럼 날짜가 걸린 수정**을 제때 못 내보낸다. 12/29 마감 직전에 계산 버그를 발견하면 심사 1~3일이 그대로 손실이다.

### B를 버린 이유 (Phase 1에서만) — 가장 아까운 후보

Re.Pack 5는 **Webpack/Rspack + Module Federation 2를 RN에 가져오는 Metro 대체 도구**다([Re.Pack 5 발표](https://www.callstack.com/blog/announcing-re-pack-5-with-rspack-module-federation)). MF2의 동적 타입 힌트·Manifest·Federation Runtime·Runtime Plugin System을 RN 런타임에 통합했고 **웹과 같은 API**를 쓴다. 즉 **토스가 자체 구축한 것의 제품화 버전**이고, 우리가 D를 버린 이유를 그대로 해결한다.

**안 되는 것:** **Expo를 공식 지원하지 않는다**([repack#1396](https://github.com/callstack/repack/issues/1396), [discussion#1309](https://github.com/callstack/repack/discussions/1309)). `RN-REQ-001`이 Expo를 고른 이유는 **네이티브 빌드·서명 전담이 0명**이기 때문이다. B를 지금 고르면 그 문제가 되돌아온다.

**우리에게 지금 안 맞은 결정적 이유:** 화면이 **7개**다. 번들 분리로 얻는 "필요할 때만 다운로드"의 이득이 설정·운영 비용보다 작다. **번들 크기가 예산을 넘긴 적이 없다** — 넘긴 뒤에 도입하는 것이 순서다.

### A가 우리에게 맞은 이유 3개

1. **MFE로 얻고 싶은 것의 대부분을 준다.** "스토어 심사 없이 배포"가 값의 8할이고 OTA가 그걸 준다.
2. **`RN-REQ-001`의 Expo 결정과 충돌하지 않는다.** 추가 도구가 0개다.
3. **카나리를 채널·점진 롤아웃으로 흉내낼 수 있다.** 사용자 ≤10명이면 "10%에 먼저"가 사실상 "1명에게 먼저"이고, 그건 내부 테스트 채널로 충분하다.

## Requirements

### A. Phase 1 — OTA (지금 한다)

| ID | 요구사항 | 우선순위 |
|---|---|---|
| FR-1 | `expo-updates`를 설정한다. JS 번들을 OTA로 배포하고, **네이티브 변경이 없으면 스토어를 거치지 않는다** | Must |
| FR-2 | 채널을 분리한다: `internal`(본인) · `production`(초대된 지인). 릴리스는 `internal` → 확인 → `production` 순서 | Must |
| FR-3 | **점진적 롤아웃**을 쓴다. 금액·세금 계산이 바뀌는 릴리스는 반드시 단계적으로 | Must |
| FR-4 | **Hermes를 켠다.** 사전 컴파일로 초기 로딩을 줄인다 | Must |
| FR-5 | **번들을 쪼개지 않는다.** §B 조건 없이 쪼개면 설정만 늘고 배포가 느려진다 | Must |
| FR-6 | OTA 적용 시점을 사용자에게 알린다. **금액 화면이 열려 있는 동안 번들을 바꾸지 않는다** — 화면의 숫자와 코드가 어긋난다 | Must |
| FR-7 | 롤백 경로를 확보한다. 이전 번들로 되돌리는 것이 명령 하나여야 한다 | Must |
| FR-8 | **네이티브 변경을 OTA로 내보내지 않는다.** 버전 게이트(§C)가 강제한다 | Must |

### B. Phase 2 — 번들 분리 도입 조건

**셋 중 하나라도 생기면 검토를 시작한다. 감으로 판단하지 않는다.**

| ID | 조건 | 측정 |
|---|---|---|
| FR-10 | **JS 번들이 4MB를 넘는다** (Hermes 바이트코드 기준) | `performance-rn.md` §1 |
| FR-11 | **콜드 스타트가 2s를 넘는다** (저가 Android 실기기) | 동일 |
| FR-12 | **릴리스 주기가 다른 기능이 생긴다** — 웹의 세금 zone과 같은 경계. 법령 파라미터만 바꿔 배포하고 싶어질 때 | 릴리스 로그 |
| FR-13 | 위 조건 없이 Phase 2를 시작하지 않는다 | — |

### C. Phase 2 도입 시 규칙 (미리 정한다)

| ID | 요구사항 | 우선순위 |
|---|---|---|
| FR-20 | 번들 경계는 **웹 zone 경계와 같은 기준**: ① 릴리스 주기가 다르다 ② 자주 오가지 않는다 ③ 다른 번들에 실릴 이유가 없는 무거운 코드. **세 조건 전부** | Must |
| FR-21 | 첫 후보는 **`tax` 하나**다. 웹에서 이미 같은 판단을 했다(`ADR-001` §3-4) | Must |
| FR-22 | **Shared 번들에는 `react` · `react-native` · `@repo/ui-native` · `@repo/tokens`만** 넣는다. 기능 코드가 Shared에 들어가면 분리의 의미가 없다 | Must |
| FR-23 | Service 번들 로딩 실패 시 **그 화면만** 실패한다. 앱이 죽지 않는다 | Must |
| FR-24 | 도구 선택 시점에 **Metro의 MF 지원 상태를 먼저 확인한다**([metro#1480](https://github.com/facebook/metro/issues/1480)). 들어와 있으면 Re.Pack 대신 그것을 쓴다 — Expo 비호환 문제가 사라진다 | Must |
| FR-25 | Re.Pack을 고르면 **Expo 비호환을 어떻게 처리할지 먼저 결정**한다: ① bare RN으로 내려온다(EAS 빌드·OTA를 잃는다) ② 커뮤니티 조합을 쓴다([expo-repack-federation](https://github.com/MuhammedBasith/expo-repack-federation), 공식 아님). **결정 없이 착수하지 않는다** | Must |

### D. 하지 않는 것

| ID | 요구사항 |
|---|---|
| FR-30 | **자체 번들 어드민·CDN·카나리 인프라를 만들지 않는다.** 토스는 전담 4명이 있었다 |
| FR-31 | **ESBuild 파이프라인을 직접 만들지 않는다.** Phase 2에서 Rspack(Re.Pack) 또는 Metro를 쓴다 |

## 버전 게이트 (Phase 1부터 필요하다)

OTA를 쓰면 **JS와 네이티브 버전이 어긋날 수 있다.**

| ID | 요구사항 | 우선순위 |
|---|---|---|
| FR-40 | 서버가 **최소 지원 네이티브 버전**을 응답에 담는다(`device` 컨텍스트, F007) | Must |
| FR-41 | 앱이 그보다 낮으면 **업데이트 안내 화면**을 띄우고 진행을 막는다 | Must |
| FR-42 | OTA 번들이 새 네이티브 API를 쓰면 게이트를 올린다. **이 판정을 사람이 잊으므로 릴리스 체크리스트에 넣는다**(`RN-REQ-003`) | Must |

## Non-Functional

| 구분 | 요구사항 |
|---|---|
| 성능 | OTA 번들 다운로드 3s(LTE). 번들 4MB 이하. `performance-rn.md` |
| 안전 | 금액·세금 릴리스는 점진 롤아웃 필수. 롤백이 명령 하나 |
| 관측성 | OTA 적용률·실패율, 번들 크기 추이, 콜드 스타트 분포. **번들 크기를 릴리스마다 기록**한다 — Phase 2 판정의 근거다 |

## Acceptance Criteria

- [ ] `expo-updates`로 JS 변경이 스토어를 거치지 않고 배포된다
- [ ] 채널이 `internal` · `production` 2개다
- [ ] 점진적 롤아웃이 동작한다 (일부에게만 적용됨을 확인)
- [ ] Hermes가 켜져 있다
- [ ] 이전 번들로 롤백하는 절차가 문서화되고 **1회 실행 검증**되었다
- [ ] 금액 화면이 열려 있는 동안 번들이 교체되지 않는다
- [ ] 네이티브 버전이 최소 요구보다 낮으면 업데이트 안내 화면이 뜬다
- [ ] **번들 크기가 릴리스마다 기록된다** (Phase 2 판정 근거)
- [ ] 번들이 4MB 이하이고 콜드 스타트가 2s 이하다 (측정값 기록)
- [ ] Phase 2 도입 조건(FR-10~12)이 문서에 있고, 조건 미달 상태에서 번들 분리가 0건이다

## Open Questions

- **Expo 점진적 롤아웃의 정확한 단위와 제어 방법.** 채널·브랜치 기반인지 퍼센트 지정인지 실제 설정으로 확인 필요. FR-3의 구현이 여기서 갈린다.
- 사용자 ≤10명에서 "10% 롤아웃"이 의미가 있는가. **`internal` 채널 1명 → `production` 9명**이 실질적인 카나리일 수 있다. 그러면 FR-3을 채널 순서로 단순화한다.
- Metro의 MF 지원([metro#1480](https://github.com/facebook/metro/issues/1480)) 진행 상태. **들어오면 Phase 2의 비용이 크게 낮아지고 Expo 비호환 문제가 사라진다.** 분기마다 확인한다.
- 금액 화면 열림 중 번들 교체 방지(FR-6)를 어떻게 구현할지. `expo-updates`의 적용 시점 제어(다음 콜드 스타트 vs 즉시) 옵션 확인 필요.
