## Summary

F007의 성능은 **앱이 얼마나 빨리 쓸 수 있게 되는가**다. 등록·게이트·OTA 확인은 전부 **시작을 막지 않아야** 한다. 하나라도 시작 경로에 직렬로 들어가면 콜드 스타트 예산이 무너진다.

## 예산

| 지표 | 조건 | 목표 | 상한 |
|---|---|---|---|
| 콜드 스타트 → 첫 프레임 | 저가 Android 실기기 | **2.0s** | 3.0s |
| 콜드 스타트 → 홈 내용 표시 | 캐시 있음 | 2.3s | 3.5s |
| 웜 스타트 | — | 600ms | 1.0s |
| 탭 전환 | — | 200ms | 400ms |
| 푸시 탭 → 목적 화면 (콜드) | — | 2.5s | 3.5s |
| 푸시 탭 → 목적 화면 (웜) | — | 500ms | 900ms |
| 오프라인 캐시 읽기 (복호화 포함) | 저가 Android | 80ms | 200ms |
| 게이트 조회 | 캐시(BFF) 히트 | 100ms | 400ms |
| 기기 등록 | 백그라운드 | — | **시작을 막지 않음** |
| OTA 확인 | 백그라운드 | — | **시작을 막지 않음** |
| OTA 다운로드 | LTE | 3s | 8s |
| JS 번들 (Hermes) | — | **4MB** | 6MB |
| 리스트 스크롤 | — | 60fps | 55fps |

기준 기기: Android — Galaxy A34급 / iOS — iPhone 12.

## Requirements

### A. 시작 경로 (핵심)

| ID | 요구사항 | 우선순위 |
|---|---|---|
| FR-1 | **기기 등록이 시작 경로에 직렬로 들어가지 않는다.** 첫 프레임 이후 백그라운드 | Must |
| FR-2 | **OTA 확인이 시작을 막지 않는다.** `checkAutomatically`를 시작 차단 모드로 두지 않는다 | Must |
| FR-3 | 게이트 조회는 **첫 프레임과 병렬**이다. 응답 전까지 앱이 동작한다 | Must |
| FR-4 | 첫 프레임은 **캐시된 홈**을 그린다. 네트워크를 기다리지 않는다 | Must |
| FR-5 | 스플래시 유지 시간이 **네트워크에 의존하지 않는다** | Must |
| FR-6 | 시작 경로의 동기 작업 총합이 **200ms 이하**다 | Must |
| FR-7 | 위 항목을 **시작 트레이스로 검증**한다. span이 겹쳐야 한다 | Must |

**왜**: 등록·게이트·OTA를 전부 시작에 직렬로 넣으면 각 300ms만 잡아도 1초가 그냥 사라진다. 셋 다 **없어도 앱이 동작하는 것들**이므로 시작을 막을 이유가 없다.

### B. 번들

| ID | 요구사항 | 우선순위 |
|---|---|---|
| FR-10 | Hermes + 바이트코드 프리컴파일 | Must |
| FR-11 | 화면 단위 lazy 등록. **탭 3개 외 화면이 초기 번들에 없다** | Must |
| FR-12 | 설정·알림 목록·업데이트 모달은 lazy다 | Must |
| FR-13 | 폰트 서브셋을 쓴다. 전체 웨이트를 넣지 않는다 | Should |
| FR-14 | CI에서 번들 크기 회귀를 검사하고 **4MB 초과 시 실패**한다 | Must |
| FR-15 | 미사용 네이티브 모듈을 제거한다 | Should |

### C. 오프라인 캐시

| ID | 요구사항 | 우선순위 |
|---|---|---|
| FR-20 | 캐시 읽기가 **80ms 이내**다(복호화 포함) | Must |
| FR-21 | 복호화를 **홈 렌더에 필요한 부분만** 한다. 전체 트리 복호화가 0건이다 | Should |
| FR-22 | 캐시 쓰기는 **비동기**고 UI를 막지 않는다 | Must |
| FR-23 | 캐시 크기 상한 5MB. 초과 시 오래된 것부터 버린다 | Must |
| FR-24 | 캐시 읽기 실패가 **빈 화면이 아니라 로딩**으로 이어진다 | Must |

### D. OTA

| ID | 요구사항 | 우선순위 |
|---|---|---|
| FR-30 | 다운로드가 **백그라운드**고 사용 중 프레임을 떨어뜨리지 않는다 | Must |
| FR-31 | 적용은 다음 실행이 기본이다. **금액 계산 변경만 즉시 재시작** | Must |
| FR-32 | 즉시 재시작 시 **사용자에게 안내**하고 진행 중 작업을 잃지 않는다 | Must |
| FR-33 | OTA 실패가 앱을 막지 않는다. 기존 번들로 계속 동작한다 | Must |
| FR-34 | 적용률·실패율·다운로드 시간을 수집한다 | Must |

### E. 푸시 → 화면

| ID | 요구사항 | 우선순위 |
|---|---|---|

| FR-41 | 목적 화면의 데이터 조회가 **화면 전환과 병렬**이다 | Must |
| FR-42 | 딥링크 재검증이 화면 표시를 막지 않는다. 셸 먼저, 검증 결과 나중 | Must |
| FR-43 | `push_tap → target_visible`을 콜드/웜 구분해 트레이스한다 | Must |

## Acceptance Criteria

- [ ] **기기 등록·OTA 확인·게이트 조회가 시작 경로를 막지 않는다**
- [ ] **첫 프레임이 캐시된 홈을 그리고 네트워크를 기다리지 않는다**
- [ ] 시작 경로 동기 작업 총합이 200ms 이하다
- [ ] **시작 트레이스에서 세 작업의 span이 첫 프레임과 겹친다**
- [ ] **콜드 스타트 첫 프레임이 저가 Android에서 3.0s 이내다**
- [ ] Hermes가 켜져 있고 탭 3개 외 화면이 초기 번들에 없다
- [ ] **CI가 번들 4MB 초과 시 실패한다**
- [ ] **오프라인 캐시 읽기가 80ms 이내다**
- [ ] 캐시 쓰기가 UI를 막지 않는다
- [ ] 캐시 상한 5MB가 적용된다
- [ ] 캐시 읽기 실패가 빈 화면이 아니다
- [ ] OTA 다운로드가 백그라운드고 프레임 드롭 1% 이하다
- [ ] **금액 계산 변경 릴리스만 즉시 재시작하고 진행 중 작업을 잃지 않는다**
- [ ] OTA 실패가 앱을 막지 않는다
- [ ] **푸시 탭 → 목적 화면이 콜드 3.5s / 웜 900ms 이내다**
- [ ] 딥링크 재검증이 화면 표시를 막지 않는다
- [ ] 콜드/웜 구분 트레이스가 수집된다
- [ ] 콜드 스타트 분포가 기기 등급별로 수집된다
- [ ] **번들 크기 추이가 릴리스마다 기록된다**
- [ ] 기준 기기 2종에서 릴리스마다 예산이 검증된다
- [ ] **성능 로그·트레이스에 금액·토큰이 0건이다**
- [ ] 8개 열화 시나리오가 검증된다
- [ ] iOS·Android 양쪽에서 통과한다

## Open Questions

- 캐시 부분 복호화(FR-21)는 구조가 복잡해진다. 전체 복호화가 80ms 안에 들어가면 부분 복호화를 하지 않는 편이 낫다 — 실측 후 결정.
- 콜드 스타트 2.0s 목표에 Expo 런타임 초기화가 몇 ms인지 아직 모른다. 첫 프로토타입 실측 후 예산을 재조정할 수 있다.
- `expo-updates`의 `checkAutomatically`를 `ON_LOAD`(백그라운드)로 두면 시작은 빠르지만 긴급 수정 반영이 한 실행 늦다. 금액 변경 릴리스의 "즉시 적용"과 어떻게 양립시킬지 — `RN-REQ-029` FR-43과 함께 결정한다.
