## Summary

모바일에서 이 화면의 급소는 **슬라이더 재계산이 JS 스레드를 막는 것**이다. 스레드가 하나이므로 웹보다 위험하다.

## 예산 (저가 Android 실기기 기준)

| 지점 | 예산 | 비고 |
|---|---|---|
| 자산 탭 → 세금 화면 push | **400ms** | 캐시 히트 시 즉시 |
| 세금 화면 첫 페인트 (캐시) | **200ms** | 마지막 캐시를 먼저 그린다 |
| 세금 화면 데이터 도착 | 1.2s | 집계 1콜 700ms + 네트워크 |
| 세그먼트 전환 | **100ms** | 이미 받은 데이터 |
| **연말 시가 슬라이더** | **60fps** | 클라이언트 재계산 |
| 3열 카드 리렌더 | **8ms** | 프레임 예산의 절반 |
| 슬라이더 대조 (놓을 때) | 400ms | 비동기, 프레임 차단 없음 |
| 손실수확 솔버 (버튼 → BottomSheet) | 900ms | BFF 600ms + 렌더 |
| 증빙 공유 시트 열기 | 300ms | 파일이 앱을 통과하지 않는다 |
| 딥링크 진입 → 화면 | **1s** | 콜드 스타트 포함 시 2.5s |

## 급소 1 — 슬라이더가 JS 스레드를 막는다

| ID | 요구사항 | 우선순위 |
|---|---|---|
| FR-1 | 슬라이더 값 변경을 **프레임 단위로 버퍼링**한다. 터치 이벤트마다 setState하면 스레드가 막힌다 | Must |
| FR-2 | 재계산 함수는 **순수 함수**이고 O(1)이다. 보유 종목 전부를 재계산하지 않고 **선택된 종목 하나만** 계산한다 | Must |
| FR-3 | 3열 카드를 슬라이더와 **다른 컴포넌트**에 둔다. 슬라이더 값 변경이 화면 전체를 리렌더하면 안 된다 | Must |
| FR-4 | 3열 카드를 `memo`로 감싼다. **여기는 예방적 메모가 정당한 자리다** — 슬라이더가 초당 수십 회 갱신한다 | Must |
| FR-5 | 재계산을 **`InteractionManager.runAfterInteractions`에 넣지 않는다** — 슬라이더는 즉시 반영이 필요하다. 대신 계산 자체를 가볍게 유지한다 | Must |
| FR-6 | `Decimal` 라이브러리를 쓰면 **프레임 예산 안에 들어오는지 측정**한다. 안 되면 `number`로 계산하고 놓을 때 서버 값으로 덮는다 | Must |
| FR-7 | 슬라이더 프레임을 실기기에서 측정하고 **60fps 유지를 기록**한다 | Must |

## 급소 2 — 첫 페인트에 네트워크를 기다리지 않는다

| ID | 요구사항 | 우선순위 |
|---|---|---|
| FR-10 | 화면 진입 시 **마지막 캐시를 먼저 그린다.** 200ms 예산 | Must |
| FR-11 | D-Day는 캐시된 날짜로 **클라이언트 계산**하므로 네트워크 없이 정확하다 | Must |
| FR-12 | 갱신 중에는 인라인 스피너만. **전체 스켈레톤으로 되돌리지 않는다** | Must |
| FR-13 | 캐시가 없으면(첫 진입) 세그먼트별 스켈레톤 | Must |

## 급소 3 — 솔버는 BottomSheet로 분리

| ID | 요구사항 | 우선순위 |
|---|---|---|
| FR-20 | 솔버를 화면에 인라인으로 쌓지 않는다. **버튼 → BottomSheet** | Must |

| FR-22 | 후보 3개의 종목 목록을 접어서 렌더한다. 펼칠 때만 리스트를 만든다 | Must |
| FR-23 | `AbortSignal`로 시트를 닫으면 취소한다 | Must |

## Acceptance Criteria

- [ ] 자산 탭 → 세금 push가 400ms 이내다 (측정값 기록)
- [ ] 캐시 첫 페인트가 200ms 이내다
- [ ] 세그먼트 전환이 100ms 이내이고 서버 호출이 0건이다
- [ ] **슬라이더가 저가 Android 실기기에서 60fps를 유지한다** (측정값 기록)
- [ ] 슬라이더 값 변경이 프레임 단위로 버퍼링된다
- [ ] 재계산이 선택된 종목 하나만 계산한다
- [ ] 슬라이더 값 변경이 화면 전체를 리렌더하지 않는다 (Profiler 확인)
- [ ] 3열 카드가 `memo`로 감싸져 있다
- [ ] `Decimal` 사용 시 프레임 예산 안에 들어옴이 측정되어 있다
- [ ] 갱신 중 전체 스켈레톤으로 되돌아가지 않는다
- [ ] 오프라인에서 D-Day가 정확하다
- [ ] 솔버가 BottomSheet로 열리고 버튼이 `loading`이다
- [ ] 시트를 닫으면 솔버 요청이 취소된다
- [ ] 보유 목록이 `FlatList`이고 행이 `memo`이고 key가 index가 아니다
- [ ] 증빙 파일이 앱 메모리를 통과하지 않는다 (메모리 프로파일 확인)
- [ ] 언마운트 시 구독·타이머가 정리된다
- [ ] 오프라인 캐시 렌더가 200ms 이내다
- [ ] persist 저장소 크기가 제한된다
- [ ] **세금 화면의 번들 비중이 릴리스마다 기록된다**
- [ ] 신규 의존성 번들 증가분이 기록되어 있다
- [ ] 측정이 릴리스 빌드 + 기준 기기로 수행되었다
- [ ] 로그에 세금 금액이 0건이다

## Open Questions

- `Decimal`이 프레임 예산 안에 들어오는가. 안 되면 **`number`로 계산하고 놓을 때 서버 값으로 덮는** 방식으로 정확도를 확보한다 — 그러면 조작 중 표시값이 서버와 미세하게 다를 수 있고, 그 사실을 표시해야 하는지 판단이 필요하다.
- 슬라이더 대신 **미리 정의된 시나리오 버튼**(−20%/0/+20%/+50%)이 모바일에서 더 나을 수 있다. 프레임 문제가 사라지고 사용성도 나을 가능성이 있다 → `RN-REQ-012` Open Question과 동일.
- persist 저장소에 금액이 평문으로 남는 문제(`RN-REQ-014` Open Question).
