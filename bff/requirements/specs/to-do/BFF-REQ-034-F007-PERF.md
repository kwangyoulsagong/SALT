## Summary

모바일 홈은 **스트리밍이 없다.** 웹은 셸을 먼저 보내고 블록을 흘릴 수 있지만, 앱은 응답 하나를 기다린다. 그래서 **BFF 홈 응답 시간이 곧 앱의 체감 속도**다. 이게 F007에서 BFF 성능이 웹보다 중요한 이유다.

## 예산

| 경로 | 목표 (p95) | 상한 |
|---|---|---|
| `GET /bff/home` (모바일 단일 응답) | **800ms** | 2s |
| `POST /device/register` | 100ms | 300ms |
| `GET /device/version-gate` (캐시 히트) | **5ms** | 20ms |
| `GET /device/version-gate` (미스) | 50ms | 200ms |
| `GET/PATCH /notification-prefs` | 80ms | 250ms |
| `GET /app/notifications` (20건) | 150ms | 400ms |
| BFF 자체 오버헤드(집계 로직) | 20ms | 50ms |

## Requirements

### A. 홈 단일 응답

| ID | 요구사항 | 우선순위 |
|---|---|---|
| FR-1 | 5블록 병렬 호출의 **총 시간이 가장 느린 블록 + 오버헤드**다. 직렬 구간이 0건이다 | Must |
| FR-2 | 블록 타임아웃 1.5s가 **전체 상한 2s를 보장**한다 | Must |
| FR-3 | 직렬 호출 0건임을 **트레이스로 검증**한다 (span 겹침 확인) | Must |
| FR-4 | 응답 직렬화가 50ms를 넘지 않는다. 페이로드 **100KB 이하** | Must |
| FR-5 | gzip/brotli 압축을 적용한다 | Must |
| FR-6 | 블록별 소요 시간을 응답 헤더 `Server-Timing`에 남긴다 | Should |

### B. 게이트 캐시

| ID | 요구사항 | 우선순위 |
|---|---|---|
| FR-10 | 게이트 캐시 히트율 **95% 이상**이다 | Must |
| FR-11 | 캐시 조회가 **동기 메모리 접근**이다. 히트 경로에 네트워크가 없다 | Must |
| FR-12 | 캐시 갱신은 **백그라운드**로 한다. 요청이 갱신을 기다리지 않는다(stale-while-revalidate) | Must |
| FR-13 | 게이트 미들웨어가 **모든 요청에 붙지 않는다.** BFF는 헤더 pass-through만 하므로 판정 비용이 0이다 | Must |

### C. 등록 경로

| ID | 요구사항 | 우선순위 |
|---|---|---|
| FR-20 | 등록은 **upstream 1회**다. 추가 조회가 0건이다 | Must |
| FR-21 | 등록이 홈 응답과 **커넥션 풀을 경쟁하지 않게** upstream 풀을 분리하거나 상한을 둔다 | Should |
| FR-22 | 앱 시작 시 등록과 홈 조회가 **병렬**로 가능하다. BFF가 직렬화하지 않는다 | Must |
| FR-23 | 등록 rate limit은 서버가 한다. BFF가 중복으로 걸지 않는다 | Must |

### D. 세금 시즌

| ID | 요구사항 | 우선순위 |
|---|---|---|
| FR-30 | 푸시 도착 직후 **동시 진입 스파이크**를 견딘다. 전 사용자가 1분 내 앱을 여는 경우 | Must |
| FR-31 | 홈 블록 중 세금 블록만 느려지는 상황에서 **나머지 예산이 유지**된다 | Must |
| FR-32 | 12월에는 홈 p95 알람 임계를 **1.2s**로 낮춘다 | Should |
| FR-33 | 서킷 브레이커가 열려도 응답 시간이 **오히려 빨라진다**(즉시 `failed`) | Must |

### E. 리소스

| ID | 요구사항 | 우선순위 |
|---|---|---|
| FR-40 | upstream 커넥션을 keep-alive로 재사용한다 | Must |
| FR-41 | 홈 집계에서 **응답 본문을 두 번 파싱하지 않는다** | Must |
| FR-42 | 큰 페이로드(알림 목록)에 스트림 파싱을 쓰지 않아도 되게 `limit`을 강제한다(최대 50) | Must |
| FR-43 | BFF 메모리 사용이 요청 수에 선형으로 늘지 않는다(캐시 상한) | Must |

### F. 측정

| ID | 요구사항 | 우선순위 |
|---|---|---|
| FR-50 | 홈 p50/p95/p99 · 블록별 지연 · 블록별 실패율을 대시보드에 노출한다 | Must |
| FR-51 | 게이트 캐시 히트율을 노출한다 | Must |
| FR-52 | **모바일과 웹 트래픽을 `X-Platform`으로 구분해서** 집계한다 | Must |
| FR-53 | 메트릭 레이블에 `userId`·토큰이 0건이다 | Must |

## 부하 시나리오

| 시나리오 | 조건 | 기대 |
|---|---|---|
| 푸시 후 동시 진입 | 전 사용자 1분 내 홈 조회 | p95 2s 이내, 에러 0건 |
| 세금 블록 3s 지연 | 1블록만 | 홈 응답 1.6s 이내(1.5s 타임아웃 + 오버헤드) |
| 서버 전면 다운 | 전 블록 5xx | 홈 응답 **200ms 이내**(즉시 실패), 200 상태 |
| 게이트 upstream 다운 | 캐시 히트 | 5ms 유지 |
| 알림 목록 50건 | 최대 limit | 400ms 이내 |
| 앱 시작 동시 3콜 | 등록+게이트+홈 | 직렬화 0건, 총 시간 = max |

## Acceptance Criteria

- [ ] **5블록 병렬 호출에 직렬 구간이 0건이고 트레이스로 검증된다**
- [ ] 블록 타임아웃 1.5s가 전체 2s 상한을 보장한다
- [ ] 홈 페이로드가 100KB 이하이고 압축된다
- [ ] `Server-Timing`에 블록별 시간이 있다
- [ ] **게이트 캐시 히트율이 95% 이상이고 히트 경로에 네트워크가 없다**
- [ ] 캐시 갱신이 백그라운드다
- [ ] 등록이 upstream 1회다
- [ ] **앱 시작 시 등록·게이트·홈이 병렬 가능하다**
- [ ] BFF가 rate limit을 중복으로 걸지 않는다
- [ ] **푸시 후 동시 진입에서 p95 2s 이내, 에러 0건이다**
- [ ] 세금 블록만 느릴 때 나머지 예산이 유지된다
- [ ] **서버 전면 다운에서 홈이 200ms 이내 200으로 응답한다**
- [ ] 서킷 브레이커가 열리면 응답이 빨라진다
- [ ] upstream keep-alive가 적용된다
- [ ] 알림 목록 `limit`이 50으로 강제된다
- [ ] BFF 메모리가 요청 수에 선형으로 늘지 않는다
- [ ] **`X-Platform`으로 모바일·웹이 구분 집계된다**
- [ ] 메트릭 레이블에 `userId`·토큰이 0건이다

## Open Questions

- 홈 800ms 목표는 서버 5블록이 각각 500ms 이내여야 성립한다. 세금 블록(F002)이 그 안에 들어가는지 아직 미검증.
- 모바일도 청크 응답(NDJSON)으로 받으면 첫 블록을 먼저 그릴 수 있다. RN에서 구현 비용 대비 이득이 있는지 — `BFF-REQ-031` Open Question과 연결된다.
