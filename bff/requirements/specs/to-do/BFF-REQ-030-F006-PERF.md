## Summary

F006의 BFF 급소는 **동시 SSE 스트림이 메모리와 커넥션을 잡는 것**이다. 홈은 서버가 조립하므로 BFF 부하가 낮다.

## 예산

| 엔드포인트 | 예산 | 내역 |
|---|---|---|
| `POST /api/app/coach/messages` | **250ms** | 서버 200ms + BFF 20ms |
| **첫 토큰 도착** | **1s** | 서버 첫 토큰 + BFF 통과 |
| 델타 전달 지연 | **버퍼링 0** | 즉시 통과 |
| `GET /api/app/home` | **450ms** | 서버 400ms + BFF 20ms |
| 홈 블록 개별 | 350ms | |
| 대화 목록 | 150ms | |
| 메시지 목록(30) | 200ms | |
| 알림 | 150ms | |
| 패널 배치 | 100ms | |
| **BFF가 얹는 지연** | **20ms 이하** | 스트림은 통과 지연 5ms 이하 |

## 급소 1 — 동시 스트림

| ID | 요구사항 | 우선순위 |
|---|---|---|
| FR-1 | 스트림당 **메모리를 측정**한다. 버퍼가 쌓이면 backpressure 문제다 | Must |
| FR-2 | **`pipeline()`으로 파이프**해 backpressure를 처리한다. 수동 `write()`는 느린 클라이언트에서 메모리가 찬다 | Must |
| FR-3 | 동시 스트림 상한을 둔다. 사용자 ≤10명 × 1 = 10이므로 **20이면 넉넉**하다 | Must |
| FR-4 | 초과 시 429 + 안내 | Must |
| FR-5 | **클라이언트 종료 시 서버 요청을 끊는다.** 안 하면 스트림이 쌓인다 | Must |
| FR-6 | 스트림 타임아웃 60s. 좀비 스트림이 남지 않게 | Must |
| FR-7 | 동시 스트림 수와 평균 지속 시간을 측정한다 | Must |

## 급소 2 — 버퍼링 제거

| ID | 요구사항 | 우선순위 |
|---|---|---|
| FR-10 | **압축을 끈다.** gzip이 토큰을 모아 버린다. BFF↔서버, BFF↔클라이언트 **양쪽** | Must |
| FR-11 | `X-Accel-Buffering: no`를 설정한다 | Must |
| FR-12 | Express의 응답 버퍼링을 끄고 즉시 flush한다 | Must |
| FR-13 | **델타 통과 지연을 측정**한다. 5ms를 넘으면 어딘가 버퍼링되고 있다 | Must |
| FR-14 | `ping` 15초로 프록시 유휴 종료를 막는다 | Must |

## 급소 3 — 홈

| ID | 요구사항 | 우선순위 |
|---|---|---|
| FR-20 | 서버가 조립하므로 **BFF는 1회 호출**이다. 5번 부르지 않는다 | Must |
| FR-21 | 웹 블록별은 서버 블록 엔드포인트 1:1 프록시. **5개면 서버 호출 5회**가 된다 → 측정 후 집계로 바꿀지 판단 | Must |
| FR-22 | 타임아웃 600ms | Must |
| FR-23 | 홈을 캐시하지 않는다 | Must |
| FR-24 | 홈 응답 크기를 측정한다. `holdingsPreview` 5개 상한이 지켜지는지 | Must |

## 응답 크기

| ID | 요구사항 | 우선순위 |
|---|---|---|
| FR-30 | 메시지 목록에 `cardPayload`가 포함되면 응답이 커진다. **크기를 측정**하고 30건 기준 상한을 확인한다 | Must |
| FR-31 | `content`가 길면 목록이 커진다. 페이지 크기 30이 적절한지 측정 | Must |
| FR-32 | 홈 `holdingsPreview` 5개 상한 | Must |
| FR-33 | SSE는 압축하지 않으므로 **텍스트 크기가 그대로 전송**된다. 토큰 수가 곧 대역폭이다 | Must |

## 커넥션

| ID | 요구사항 | 우선순위 |
|---|---|---|
| FR-40 | SSE가 커넥션을 **최대 60초** 잡는다. 동시 20개면 커넥션 20개다 | Must |
| FR-41 | 일반 요청이 스트림 때문에 굶지 않는지 측정한다 | Must |
| FR-42 | 서버로 나가는 커넥션 풀 크기를 확인한다. 스트림 20개 + 일반 요청이 동시에 나간다 | Must |

## 관측성

| ID | 요구사항 | 우선순위 |
|---|---|---|
| FR-50 | 측정: **첫 토큰 지연**, **델타 통과 지연**, 동시 스트림 수·지속 시간, 스트림 취소율, 429 발생률, 홈 p95·블록별 `unavailable` 발생률, 응답 크기 | Must |
| FR-51 | **BFF가 얹는 지연**을 스트림과 일반 요청 각각 측정한다 | Must |
| FR-52 | SSE 본문·홈 금액을 로그에 남기지 않는다 | Must |
| FR-53 | 성능 수정 커밋에 before/after 수치를 남긴다 | Must |

## Acceptance Criteria

- [ ] 스트림당 메모리가 측정되고 클라이언트가 느려도 늘지 않는다 (backpressure 확인)
- [ ] **`pipeline()`으로 파이프된다** (수동 `write()` 0건)
- [ ] 동시 스트림 상한이 있고 초과 시 429다
- [ ] **클라이언트 종료 시 서버 요청이 끊긴다**
- [ ] 스트림 타임아웃 60s이고 좀비 스트림이 0건이다
- [ ] 동시 스트림 수·지속 시간이 측정된다
- [ ] **양쪽 구간 압축이 꺼져 있다**
- [ ] `X-Accel-Buffering: no`가 있다
- [ ] **델타 통과 지연 < 5ms** (측정값 기록)
- [ ] `ping`이 15초 주기다
- [ ] **첫 토큰 p95 < 1s** (측정값 기록)
- [ ] 홈이 서버를 1회 부른다
- [ ] 블록별 사용 시 서버 호출 수가 측정되어 있다
- [ ] `GET /api/app/home` p95 < 450ms (측정값 기록)
- [ ] 홈이 캐시되지 않는다
- [ ] 메시지 목록 응답 크기가 측정되어 있다
- [ ] `holdingsPreview`가 5개 이하다
- [ ] 일반 요청이 스트림 때문에 굶지 않는다 (측정)
- [ ] 서버 커넥션 풀 크기가 확인되어 있다
- [ ] 관측 항목 7종이 있다
- [ ] **BFF가 얹는 지연 < 20ms** (일반), **< 5ms** (스트림 통과)
- [ ] SSE 본문·금액이 로그에 0건이다

## Open Questions

- **웹이 블록별 5개를 부르면 서버 호출이 5회**다(FR-21). 서버 홈 조립이 400ms인데 5번이면 서버 CPU가 2s를 쓴다 → **웹도 집계 1콜 + 스트리밍 SSR로 블록을 나누는 것**이 나을 수 있다. `FE-REQ-008`의 판정과 함께 봐야 한다.
- 메시지 목록에 `cardPayload`를 포함할지(`DB-REQ-024` Open Question). 크기 측정이 답을 준다.
- Express에서 SSE backpressure 처리 방법 실측 필요.
