# BFF-REQ-040 회고 — 국내 주식 화면 계약 · 실시간 중계 (2026-10-08)

## 잘 유지된 점

- route(path · 미들웨어) → controller(형식 검증 · 취소) → service(호출 · 실패 규칙) → viewmodel(순수 함수) 경계. 컨트롤러가 backendApi 를 부르지 않는다
- 실패 규칙을 전망(`BFF-REQ-037`)과 같게 — 4xx 그대로 · 5xx/타임아웃/계약 깨짐 `unavailable`. 새 상태는 `disabled` 하나뿐
- 실시간을 업비트 경로와 섞지 않고 연결 단위로 가뒀다 — 연결 종료 · 하트비트 종료 · 프로세스 종료 세 곳에서 upstream 을 끊는다
- 라우터 순서를 실제 Express 앱 테스트로 고정했다(`/kr` vs 코인 `/:symbol`, `/search` vs `/:code`)

## 기획과 달라진 것

| 기획 | 실제 | 이유 |
|---|---|---|
| BFF 캐시(정규장 1s · 그 외 60s) | 없음 | 응답이 소유자 판정에 걸린다 — 공유 캐시는 새고 토큰별 캐시는 히트가 없다. 서버 p95 22ms |
| SSE 를 BFF 내부 토큰으로 하나 | WS 연결마다 그 연결의 토큰으로 | 슬라이스 1 이 서버 SSE 를 사용자 JWT + 소유자로 열었다 |
| `lastTradeAt` · `nextCursor` · `w52High` · `1h` 봉 | `lastCloseAt` · `nextOffset` · `week52High` · 1d/5m 만 | 서버가 먼저 섰다. 이름을 바꾸면 두 계약이 생긴다 |

## 남은 기술부채

- **토큰 만료 중 연결 유지** — 서버는 SSE 를 열 때만 인증한다. 만료된 토큰의 스트림도 끊길 때까지 흐른다. 다시 열 때 401 이면 멈춘다(화면이 새 토큰으로 다시 구독). 소유자 전용이라 위험은 작다
- **소유자 탭마다 upstream 하나** — 탭 3개면 서버 SSE 3개. 상한 20 으로 막았다. 같은 토큰을 묶는 공유는 토큰 갱신 시점이 달라 하지 않았다
- **업비트에 6자리 코드를 넣으면 거부된다는 근거는 실측하지 않았다** — 섞지 않는 이유 하나로 적어 뒀다
- `@repo/core` 타입이 아직 없다 — 화면 슬라이스(`FE-REQ-041`) 커밋에서 더한다(기존 관례)
