# 서버 성능 규칙 (Express + Prisma)

## 0. 이 서버의 조건

| 조건 | 결과 |
|---|---|
| **사용자 ≤10명 (비공개·초대제)** | 동시성 튜닝·수평 확장이 무의미하다. 커넥션 풀도 작게 |
| **LLM 호출이 수 초~수십 초** | 최대 병목이다. 트랜잭션·스레드 설계를 여기에 맞춘다 |
| **반사실 계산이 거래 5,000건 × 일봉 3,000개** | 두 번째 병목. 스냅샷으로 분리한다 |
| **워커 6개 이상이 상시 돈다** | 시세·지표·환율·뉴스·스냅샷·알림. DB 커넥션을 나눠 쓴다 |

## 1. 예산

| 작업 | 예산 | 초과 시 |
|---|---|---|
| 단순 조회 (D-Day · 보유 · 설정) | 100ms | 인덱스·Projection 점검 |
| 목록 조회 (거래·알림·뉴스) | 300ms | 페이징 필수 |
| 세금 콕핏 전체 | 600ms | lot 집계를 Projection으로 |
| 손실수확 솔버 (종목 50개) | 500ms | 후보 수를 줄이거나 근사 |
| 반사실 전체 계산 (스냅샷 미스) | **1.5s (p95)** | 스냅샷 우선 렌더 |
| 반사실 스냅샷 히트 | 200ms | |
| 주간 계획 조회 | 250ms | 지표는 일 1회 갱신 → 전부 캐시 히트 |
| 김프 | 실시간, 30초 캐시 | |
| 코치 추천 생성 (LLM 포함) | **6s (p95)** · 비동기 | 동기로 만들지 않는다 |
| 코치 대화 첫 토큰 | 1s | 이후 SSE 스트리밍 |
| CSV import 10,000행 | 10s | 배치 insert |

**수 초를 넘는 작업은 비동기다.** 요청 하나를 붙잡고 기다리면 취소도 진행률 표시도 못 한다.

## 2. 트랜잭션 — 가장 중요한 규칙

### 외부 I/O를 트랜잭션 안에 넣지 않는다

```ts
// ❌ LLM 호출 수십 초 동안 커넥션과 락을 잡는다
await prisma.$transaction(async (tx) => {
  const ctx = await loadContext(tx, userId);
  const text = await gemini.explain(prompt);     // ← 수십 초
  await tx.investmentInsight.create({ data: { ... } });
});

// ✅ 외부 호출은 트랜잭션 밖. 저장만 짧게 감싼다
const ctx  = await loadContext(userId);           // 짧은 읽기
const text = await gemini.explain(prompt);        // 트랜잭션 없음
await prisma.$transaction((tx) => persist(tx, text));   // 짧은 쓰기
```

같은 규칙이 **거래소 API · 환율 · 지표 수집 · 뉴스 크롤링**에 전부 적용된다.

### 그 외

- `prisma.$transaction`은 **`{context}/application/`에서만** 호출한다
- **트랜잭션 안에서 파일 파싱을 하지 않는다.** CSV 10,000행 파싱은 밖에서 하고 결과만 배치 insert
- 여러 Aggregate를 수정할 때 **항상 같은 순서**로 잡는다(데드락 회피)

## 3. 조회 — Aggregate를 로드하지 않는다

```ts
// ❌ 거래 5,000건을 로드해서 수수료 합계만 쓴다
const txs = await txStore.findByUserInRange(userId, from, to);
const fee = txs.reduce((s, t) => s.plus(t.fee), Money.krw(0));

// ✅ Projection
const fee = await feeProjection.sumFeeInRange(userId, from, to);
```

`invoice`·`tax`가 특히 위험하다 — 원장 전체를 훑는 계산이 기본 동작이다.

## 4. 반사실·세금 계산은 스냅샷으로 분리한다

두 계산이 원장 전체를 훑는다. 요청마다 하면 예산을 못 지킨다.

| 계산 | 스냅샷 | 갱신 |
|---|---|---|
| 반사실 3트랙 | `CounterfactualSnapshot` | 월요일 09:00 워커 + 수동 재계산 |
| 취득가액 lot | `CostBasisLot` | 원장 import 시 재계산 |
| 지표 | `IndicatorSnapshot` | 일 1회 06:00 |
| 환율 | `FxRate` | 일 1회 |

**화면은 스냅샷을 먼저 그리고 현재가만 실시간 보정한다.** 스냅샷 미스는 `degraded`로 표시하고 계산을 비동기로 띄운다.

## 5. 페이징

- 목록 API는 **전부 페이징한다.** 예외 없다. 거래·알림·뉴스·대화 메시지는 무한히 늘어난다
- `count`가 필요 없으면 세지 않는다
- 깊은 offset 페이징을 피한다. 시간순인 것은 **커서(`createdAt` + `id`)** 로 넘긴다
- 대화 메시지는 역순 커서 페이징

## 6. 워커

- 워커는 **스케줄과 락만** 담당하고 `application`의 유스케이스를 부른다
- **분산 락을 userId 단위로** 잡는다. 같은 사용자의 반사실 계산이 두 번 동시에 돌지 않게
- **멱등이어야 한다.** 같은 시간 버킷 재실행이 row를 늘리면 안 된다(upsert)
- 실패는 **지수 백오프 3회**, 최종 실패 시 마지막 성공 상태를 유지하고 알림
- **LLM을 부르는 워커와 DB만 훑는 워커를 같은 큐에 넣지 않는다.** 앞의 것이 수십 초를 잡으면 뒤의 것이 아무 일도 못 하고 기다린다
- `year-end-snapshot.worker`는 **1회성이고 되돌릴 수 없다.** 10분 간격 6회 재시도 + 실패 시 즉시 알림 + 수동 입력 경로. **12월 중 드라이런으로 검증한다**

## 7. 캐싱

인메모리로 충분하다. **무효화 조건이 명확할 때만** 쓴다.

| 대상 | 무효화 |
|---|---|
| 지표 스냅샷 | 일 1회 갱신 — 캐시 적합 |
| 환율 | 일 1회 |
| 김프 | TTL 30초 |
| 법령 파라미터(`TaxLawConfig`) | 수동 변경 시 |
| LLM 해설 | 생성 시 1회 만들고 스냅샷에 저장. **매 요청마다 부르지 않는다** |
| 홈 조립 결과 | **캐시하지 않는다** — 매번 달라지는 것이 이 화면의 목적이다 |

## 8. 응답 크기

- **본문과 목록을 분리한다.** 거래 목록에 전후 90일 가격 배열을 담지 않고 별도 엔드포인트로 조회
- 반사실 `series`는 일별 배열이다. 기간 `all`이면 수천 개가 된다 — **표시 해상도로 다운샘플링**해서 준다
- 응답에 쓰지 않는 필드를 넣지 않는다

## 9. 측정

- 슬로우 쿼리 로그를 켜고 임계값을 예산에 맞춘다
- 느리다는 보고에 추측으로 답하지 않는다. **`EXPLAIN (ANALYZE, BUFFERS)`를 먼저 본다**(`performance-database.md`)
- 관측 항목: LLM 성공률·지연, 반사실 계산 시간, **`reconciliation` 잔차 히스토그램**, 원장 대조 오차율, 지표 `staleDays` 분포, 스냅샷 수집 성공/실패
- 성능 수정 커밋에 **before/after 수치**를 남긴다
