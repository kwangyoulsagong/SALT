## Summary

F006의 예산 두 개가 어렵다: **첫 토큰 1초**와 **홈 400ms**. 첫 토큰은 컨텍스트 조립 + LLM 응답 시작이고, 홈은 5개 소스 병렬이다.

## 예산

| 작업 | 예산 | 내역 |
|---|---|---|
| `POST /api/coach/messages` | **200ms** | 메시지 저장만. LLM을 기다리지 않는다 |
| **첫 토큰 도착** | **1s** | 컨텍스트 조립 + LLM 첫 응답 |
| 델타 간격 | 버퍼링 없이 즉시 | 프록시 버퍼링 0 |
| 카드 생성·전송 | 300ms | 게이트 판정 + 조립 |
| 부분 저장 | **20ms/회** | 단일 UPDATE |
| 완료 저장 | 50ms | 트랜잭션 1회 |
| 재연결 조회 | **50ms** | PK |
| 대화 목록 | 100ms | 커서 |
| 메시지 목록(30) | 150ms | 커서 역순 |
| **`GET /api/home`** | **400ms** | 5블록 병렬 |
| 블록 개별 | 50~150ms | 소스별 |
| 패널 배치 조회/저장 | 30ms | PK |

## 급소 1 — 첫 토큰 1초

```
요청 → 컨텍스트 조립(?) → 프롬프트 구성 → LLM 호출 → 첫 토큰
```

| ID | 요구사항 | 우선순위 |
|---|---|---|
| FR-1 | **컨텍스트 조립을 300ms 안에** 끝낸다. 각 호출 타임아웃 500ms는 상한이고 목표는 더 짧다 | Must |
| FR-2 | 라우팅이 정한 것만 부른다. **전부 부르면 조립만 1초를 넘는다** | Must |
| FR-3 | 조립을 **병렬**로 한다 | Must |
| FR-4 | 조립 결과를 **요청 스코프에서 재사용**한다. 같은 요청 안에서 두 번 부르지 않는다 | Must |
| FR-5 | **프롬프트 토큰 수가 첫 토큰 지연에 영향**한다. 상한을 두고 초과 시 히스토리를 줄인다 | Must |
| FR-6 | 첫 토큰 지연을 **조립 시간과 LLM 시간으로 분해해 측정**한다. 어느 쪽이 병목인지 알아야 한다 | Must |
| FR-7 | **후처리(답변 가드)가 문장 단위 버퍼링이면 첫 토큰이 늦어진다.** 첫 문장이 끝나야 흘릴 수 있다 → 측정 후 **첫 문장만 짧게 자르거나** 토큰 단위 검사로 바꾼다 | Must |

## 급소 2 — 홈 400ms

| ID | 요구사항 | 우선순위 |
|---|---|---|
| FR-10 | 5블록을 **병렬**로 조회한다. `await` 연쇄 0건 | Must |
| FR-11 | 각 블록이 **스냅샷/설정값**을 읽는다. 계산 0건 | Must |
| FR-12 | 블록별 타임아웃을 둔다. 가장 느린 블록이 400ms를 정한다 | Must |
| FR-13 | **홈 조립 1회 쿼리 수 ≤ 10** | Must |
| FR-14 | 청구서 블록은 **스냅샷 조회**다. 계산이 필요하면 `degraded`로 즉시 반환한다 | Must |
| FR-15 | AI 추천 블록은 **최신 insight 1건**이다. 생성하지 않는다 | Must |
| FR-16 | 홈을 캐시하지 않는다 | Must |

## 급소 3 — 스트리밍 쓰기

| ID | 요구사항 | 우선순위 |
|---|---|---|
| FR-20 | 부분 저장 **2초 또는 500자**. 메시지당 최대 30회 | Must |
| FR-21 | **트랜잭션 없이 단일 UPDATE**. 스트리밍 동안 커넥션을 잡지 않는다 | Must |
| FR-22 | `CoachMessage`·`CoachConversation`의 **autovacuum 임계값을 낮춘다.** UPDATE가 잦다 | Must |
| FR-23 | 부분 저장 지연이 **델타 전송을 막지 않는다.** 비동기로 띄우고 스트림은 계속 흐른다 | Must |
| FR-24 | 저장 실패가 스트리밍을 중단시키지 않는다 | Must |

## Acceptance Criteria

- [ ] `POST /messages` p95 < 200ms (LLM 대기 0건)
- [ ] **첫 토큰 p95 < 1s** (측정값 기록)
- [ ] **첫 토큰 지연이 조립/LLM으로 분해 측정된다**
- [ ] 컨텍스트 조립이 300ms 이내이고 병렬이다
- [ ] 라우팅이 정한 것만 부른다 (전부 호출 0건)
- [ ] 프롬프트 토큰 상한이 있고 초과 시 히스토리가 줄어든다
- [ ] **답변 가드 버퍼링이 첫 토큰 예산을 깨지 않는다** (측정 후 조정)
- [ ] 홈 5블록이 병렬이고 `await` 연쇄가 0건이다
- [ ] **홈 조립 1회 쿼리 수 ≤ 10**
- [ ] `GET /api/home` p95 < 400ms (측정값 기록)
- [ ] 청구서 블록이 스냅샷 조회이고 계산이 0건이다
- [ ] AI 추천 블록이 생성하지 않는다
- [ ] 홈이 캐시되지 않는다
- [ ] 부분 저장이 메시지당 30회 이하다 (측정값 기록)
- [ ] 부분 저장이 트랜잭션 없는 단일 UPDATE다
- [ ] **`CoachMessage` autovacuum 임계값이 낮춰져 있다**
- [ ] 부분 저장이 델타 전송을 막지 않는다
- [ ] **SSE 압축이 꺼져 있고 `X-Accel-Buffering: no`가 있다**
- [ ] `ping`이 15초 주기다
- [ ] 동시 스트림 상한이 있다
- [ ] **클라이언트 종료 시 LLM이 취소된다**
- [ ] LLM·컨텍스트 조립이 트랜잭션 밖이다
- [ ] `prisma.$transaction`이 `application` 밖에 0건이다
- [ ] 기동 시 `streaming` 정리가 기동을 막지 않는다
- [ ] 관측 항목 9종이 있다
- [ ] **토큰 수(비용)가 사용자별·일별로 집계된다**
- [ ] **답변 가드 검출 건수가 측정된다**
- [ ] 프롬프트·응답 로깅이 0건이다

## Open Questions

- **첫 토큰 1s가 달성 가능한가.** 조립 300ms + LLM 첫 응답(Gemini 실측 필요)이면 빠듯하다 → **조립을 캐시하거나 최소 컨텍스트를 더 줄여야** 할 수 있다.
- **답변 가드의 문장 단위 버퍼링과 첫 토큰 예산이 충돌한다**(FR-7). 토큰 단위 검사로 바꾸면 오검출이 늘고, 문장 단위면 늦다 → **첫 문장만 짧게 자르는 프롬프트 지시**가 절충안일 수 있다.
- 홈 400ms가 5블록 병렬로 달성 가능한가. 가장 느린 블록(청구서 스냅샷)이 50ms면 충분하지만 스냅샷 미스 시 `degraded` 경로가 빨라야 한다.
- Gemini 스트리밍의 첫 토큰 지연 실측이 필요하다.
