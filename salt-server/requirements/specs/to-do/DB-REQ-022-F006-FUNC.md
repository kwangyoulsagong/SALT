## Summary

F006의 불변식은 **스트리밍의 멱등성**에 걸린다. SSE는 자동 재연결하고, **재연결 시 같은 답변을 두 번 생성하면 비용이 두 배가 되고 답이 달라진다.**

## 불변식 목록

| ID | 불변식 | 지키는 장치 | 깨지면 |
|---|---|---|---|
| INV-1 | 재연결 시 같은 메시지를 두 번 생성하지 않는다 | `messageId` 선발급 + `status` | **LLM 비용 2배 + 답이 달라진다** |
| INV-2 | `cardPayload`는 완성 객체다 | 부분 저장 금지 | 3종 게이트가 부분 상태에서 판정된다 |
| INV-3 | `status: streaming`은 일시 상태다 | 타임아웃 후 `failed` | 영원히 스트리밍인 메시지가 남는다 |
| INV-4 | `messageCount`가 실제 메시지 수와 같다 | 트랜잭션 안 증가 | 목록이 거짓을 보여준다 |
| INV-5 | 프롬프트가 저장되지 않는다 | 스키마에 컬럼 없음 | 개인정보 노출 |
| INV-6 | 홈 블록 하나 실패가 나머지를 죽이지 않는다 | `allSettled` + 블록별 status | 화면이 빈다 |
| INV-7 | 총자산 환율 기준이 세금과 구분된다 | `FxRate.kind` | 사용자가 세금 계산과 혼동한다 |
| INV-8 | 대화 안 카드도 3종 게이트를 통과한다 | `renderable` 필드 | **정책 위반** |
| INV-9 | 대화가 주문을 실행하지 않는다 | 도메인에 주문 Port 없음 | **법적 포지셔닝 위반** |

## Requirements

### A. 재연결 멱등 (INV-1) — 이 REQ의 핵심

| ID | 요구사항 | 우선순위 |
|---|---|---|
| FR-1 | **`messageId`를 요청 시점에 선발급**한다. 클라이언트가 그 id로 스트림에 붙는다 | Must |
| FR-2 | 재연결 시 **같은 `messageId`로 붙으면 이미 생성된 부분을 이어 보낸다.** LLM을 다시 부르지 않는다 | Must |
| FR-3 | `status: complete`인 메시지에 재연결하면 **저장된 전문을 한 번에 보낸다** | Must |
| FR-4 | `status: streaming`인 메시지에 재연결하면 **이미 저장된 부분 + 이후 델타**를 보낸다 | Must |
| FR-5 | 스트리밍 중 부분 내용을 **주기적으로 저장**한다(예: 200자마다 또는 2초마다). 안 하면 재연결 시 이어 보낼 것이 없다 | Must |
| FR-6 | 같은 `messageId`로 **두 개의 LLM 호출이 동시에 돌지 않게** advisory lock 또는 상태 검사로 막는다 | Must |
| FR-7 | `Last-Event-ID`를 지원하거나 `messageId` + 오프셋으로 이어 보낸다 | Must |

### B. 카드 완성성 (INV-2, INV-8)

| ID | 요구사항 | 우선순위 |
|---|---|---|
| FR-10 | `cardPayload`를 **완성된 뒤 한 번에** 저장한다. 부분 저장 0건 | Must |
| FR-11 | `cardPayload`에 **`renderable`·`blockedReason`·`signalTrackRecord`·`failureCases`가 포함**된다. 대화 안 카드도 게이트를 통과해야 한다 | Must |
| FR-12 | 게이트 미충족이면 **카드를 만들지 않는다.** `cardPayload`가 `null`이고 답변 텍스트만 남는다 | Must |
| FR-13 | 카드는 SSE `message.card` **단일 이벤트**로 전송된다. `delta`로 흘리지 않는다 | Must |
| FR-14 | 카드가 참조하는 `insightId`를 저장한다. 다만 **카드 내용은 복사**한다 — insight가 갱신되어도 과거 대화의 카드가 바뀌면 안 된다 | Must |

### C. 스트리밍 상태 (INV-3)

| ID | 요구사항 | 우선순위 |
|---|---|---|
| FR-20 | `status: streaming`이 **60초를 넘으면 `failed`** 로 바꾼다(대화당 최대 시간) | Must |
| FR-21 | 서버 재기동 시 `streaming` 상태로 남은 메시지를 **`failed`로 정리**한다. 영원히 스트리밍인 메시지가 남으면 안 된다 | Must |
| FR-22 | 클라이언트 연결 종료 시 **LLM 호출을 취소**하고 `status`를 `failed` 또는 `complete`(부분 저장분으로)로 마감한다 | Must |
| FR-23 | `failed` 메시지도 **대화에 남긴다.** 사용자가 무엇을 물었는지 보인다 | Must |
| FR-24 | `errorCode`를 남긴다. `LLM_TIMEOUT`·`LLM_ERROR`·`CANCELLED` | Must |

### D. 카운트 정합 (INV-4)

| ID | 요구사항 | 우선순위 |
|---|---|---|
| FR-30 | `messageCount`를 메시지 생성과 **같은 트랜잭션**에서 증가시킨다 | Must |
| FR-31 | `lastMessageAt`도 같은 트랜잭션에서 갱신한다 | Must |
| FR-32 | 정합성 검증 쿼리를 두고 주기적으로 확인한다. 불일치가 있으면 재계산 | Should |

### E. 프롬프트 미저장 (INV-5)

| ID | 요구사항 | 우선순위 |
|---|---|---|
| FR-40 | **프롬프트를 저장하는 컬럼을 만들지 않는다** | Must |
| FR-41 | `content`에는 **사용자가 입력한 메시지**와 **생성된 답변**만 담는다. 시스템 프롬프트·컨텍스트는 담지 않는다 | Must |
| FR-42 | 프롬프트에 주입되는 금액·보유 정보는 **저장되지 않는다.** 필요하면 그 시점 스냅샷을 참조한다 | Must |
| FR-43 | `tokenCount`만 남긴다. 비용 관측용 | Must |

### F. 홈 부분 실패 (INV-6, INV-7)

| ID | 요구사항 | 우선순위 |
|---|---|---|
| FR-50 | 홈 5블록 중 하나가 실패하면 **그 블록만 `unavailable`** 이고 나머지가 응답한다 | Must |
| FR-51 | **금액 블록 실패 시 `0`을 반환하지 않는다.** `null` | Must |
| FR-52 | 총자산 환율은 `FxRate.kind = 'current'`를 쓴다. **세금용 `settlement_base`와 다르다** | Must |
| FR-53 | 응답에 `fxBasisCode`를 담아 화면이 툴팁으로 구분을 알린다 | Must |
| FR-54 | 홈 응답을 **캐시하지 않는다** | Must |

### G. 주문 미실행 (INV-9)

| ID | 요구사항 | 우선순위 |
|---|---|---|
| FR-60 | 대화 도메인에 **주문 관련 Port가 없다** | Must |
| FR-61 | "매수해줘"류 요청에 **계산과 근거까지만** 답한다. 프롬프트 가드 + 후처리로 강제한다 | Must |
| FR-62 | 후처리에서 **주문 실행을 약속하는 문구**를 검사한다: "주문했습니다"·"매수 완료"·"체결" | Must |
| FR-63 | 검출되면 규칙 기반 문장으로 대체한다 | Must |

## Acceptance Criteria

- [ ] `messageId`가 요청 시점에 선발급된다
- [ ] **재연결 시 LLM이 다시 호출되지 않는다** (호출 카운터로 확인)
- [ ] `complete` 메시지 재연결 시 전문이 한 번에 온다
- [ ] `streaming` 메시지 재연결 시 저장된 부분 + 이후 델타가 온다
- [ ] 스트리밍 중 부분 내용이 주기적으로 저장된다
- [ ] **같은 `messageId`로 두 LLM 호출이 동시에 돌지 않는다** (동시 요청 테스트)
- [ ] `cardPayload`가 완성 후 한 번에 저장된다 (부분 저장 0건)
- [ ] `cardPayload`에 게이트 필드 4개가 포함된다
- [ ] **게이트 미충족 시 `cardPayload`가 `null`이다**
- [ ] 카드가 SSE 단일 이벤트로 전송된다
- [ ] 카드 내용이 복사되어 insight 갱신에 영향받지 않는다
- [ ] `streaming` 60초 초과 시 `failed`가 된다
- [ ] **서버 재기동 시 `streaming` 잔여 메시지가 `failed`로 정리된다**
- [ ] 클라이언트 연결 종료 시 LLM이 취소되고 상태가 마감된다
- [ ] `failed` 메시지가 대화에 남고 `errorCode`가 있다
- [ ] `messageCount`·`lastMessageAt`이 같은 트랜잭션에서 갱신된다
- [ ] **프롬프트 저장 컬럼이 0건이고 `content`에 시스템 프롬프트가 0건이다**
- [ ] 홈 블록 하나 실패 시 나머지 4개가 응답한다
- [ ] 금액 블록 실패 시 `null`이고 `0`이 0건이다
- [ ] 총자산이 `kind = 'current'` 환율을 쓴다
- [ ] `fxBasisCode`가 응답에 있다
- [ ] 홈 응답이 캐시되지 않는다
- [ ] **대화 도메인에 주문 Port가 0건이다**
- [ ] "매수해줘" 프롬프트 10개에 주문 실행이 0건이다
- [ ] 후처리가 주문 약속 문구를 검출해 대체한다

## Open Questions

- **부분 저장 주기.** 200자마다 저장하면 쓰기가 잦고, 2초마다면 재연결 시 최대 2초분을 잃는다 → **2초 또는 500자 중 먼저 오는 것**이 기본안.
- 서버 재기동 시 `streaming` 정리를 기동 훅에서 할지 워커로 할지. **기동 훅**이 단순하다.
- 대화 컨텍스트를 어디까지 프롬프트에 넣을지. 전부 넣으면 비용과 지연이 커진다 → **최근 N턴 + 요약**이 기본안이지만 요약도 LLM 호출이다.
- 후처리 검사(FR-62)가 정상 문장을 잘못 잡을 수 있다. "체결"은 "체결 내역"처럼 정당하게 쓰인다 → **문맥 검사가 필요**할 수 있다.
