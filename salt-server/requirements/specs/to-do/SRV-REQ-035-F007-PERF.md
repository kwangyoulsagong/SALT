## Summary

이 컨텍스트의 성능 목표는 처리량이 아니라 **정시성**이다. D-1 알림이 마감 전날 도착하지 않으면 250만원 공제 한 해분이 사라진다. 나머지 지표는 그것을 지키기 위한 조건이다.

## 예산

| 엔드포인트/작업 | 목표 (p95) | 상한 |
|---|---|---|
| `POST /device/register` | 30ms | 100ms |
| `GET /device/version-gate` | 10ms | 30ms |
| `PATCH /notification-prefs` | 20ms | 60ms |
| 버전 게이트 미들웨어 오버헤드 | **1ms** | 3ms |
| `SendNotificationUseCase` 1건(전송 제외) | 10ms | 30ms |
| provider 전송 1건 | 300ms | 1.5s |
| dispatch 워커 100건 배치 | 5s | 15s |
| **D-Day 판정 워커 전체** | 3s | 30s |
| `device-reap` 배치 1,000행 | 300ms | 1s |

## Requirements

### A. 정시성 (최우선)

| ID | 요구사항 | 우선순위 |
|---|---|---|
| FR-1 | **D-1 알림은 예정 시각 + 15분 이내에 발송**된다 | Must |
| FR-2 | D-30/14/7/3은 + 2시간 이내 | Must |
| FR-3 | dispatch 워커는 **1분 주기**로 돈다. 큐 대기가 1분을 넘지 않는다 | Must |
| FR-4 | 큐 적체가 5분 이상 지속되면 **알람**이 울린다 | Must |
| FR-5 | 12월에는 알람 임계를 **2분**으로 낮춘다 | Should |
| FR-6 | 발송 지연(예정 시각 → `sentAt`) 분포를 메트릭으로 남긴다 | Must |

### B. 버전 게이트 미들웨어

| ID | 요구사항 | 우선순위 |
|---|---|---|
| FR-10 | 게이트 판정에 **DB 조회가 없다.** 인메모리 캐시 + 5분 TTL | Must |
| FR-11 | 캐시 미스에서도 요청을 막지 않는다. **판정 불가 시 통과**시킨다(fail-open) | Must |
| FR-12 | semver 비교가 O(1)이고 정규식 컴파일이 요청마다 일어나지 않는다 | Must |
| FR-13 | 헤더가 없으면 **즉시 통과**한다. 파싱 비용 0 | Must |

**왜 fail-open인가**: 게이트는 보안 장치가 아니라 UX 장치다. 캐시 실패로 전원이 잠기는 것이 낡은 앱이 잠깐 도는 것보다 훨씬 나쁘다. (렌더 게이트와 반대 방향인 이유: 저쪽은 **잘못된 정보 노출**을 막고, 이쪽은 **호환성 안내**를 할 뿐이다.)

### C. 발송 처리량

| ID | 요구사항 | 우선순위 |
|---|---|---|
| FR-20 | provider 호출을 **배치 API**로 묶는다(Expo는 100건/요청) | Must |
| FR-21 | 전송은 **트랜잭션 밖**이고 동시성 상한을 둔다(기본 10) | Must |
| FR-22 | 전송 타임아웃 5s. 초과는 `FAILED` + 재시도 대상 | Must |
| FR-23 | provider rate limit 응답(429)에 **백오프**한다. 즉시 재시도가 0건이다 | Must |
| FR-24 | dispatch 워커는 **다중 인스턴스**로 수평 확장 가능하다(SKIP LOCKED) | Must |

### D. D-Day 판정 워커

| ID | 요구사항 | 우선순위 |
|---|---|---|
| FR-30 | 사용자·자산군·마감일을 **쿼리 3회 이하**로 읽는다. N+1이 0건이다 | Must |
| FR-31 | 판정은 메모리에서 하고 INSERT를 **한 번의 `createMany`** 로 한다 | Must |
| FR-32 | 워커 전체 실행이 **30초를 넘으면 알람**을 울린다 | Must |
| FR-33 | 워커가 다른 요청 경로의 커넥션을 고갈시키지 않게 **전용 풀 상한**을 둔다 | Should |

### E. 커넥션과 리소스

| ID | 요구사항 | 우선순위 |
|---|---|---|
| FR-40 | 워커 3종이 쓰는 커넥션 합이 풀의 **30%를 넘지 않는다** | Must |
| FR-41 | 기기 등록이 초대제 규모에서 커넥션을 점유하지 않는다(단일 upsert) | Must |
| FR-42 | 토큰 복호화(KMS)를 **전송 직전 배치로** 한다. 건별 KMS 호출이 왕복 비용을 지배하지 않게 | Should |
| FR-43 | KMS 호출 실패 시 해당 배치만 `FAILED`이고 워커는 계속 돈다 | Must |

### F. 관측

| ID | 요구사항 | 우선순위 |
|---|---|---|
| FR-50 | 메트릭: 큐 깊이 · 발송 지연 p50/p95 · 성공률 · `DEAD` 전이 수 · 게이트 차단 수 | Must |
| FR-51 | **12월 전용 대시보드**를 만든다. D-30/14/7/3/1 각각의 발송 완료 여부를 한 화면에 | Must |
| FR-52 | 알람: 큐 적체 · 워커 실패 · 발송 성공률 95% 미만 · **D-Day 미발송** | Must |
| FR-53 | 메트릭·로그에 **토큰·금액이 0건**이다 | Must |

## 부하 시나리오

| 시나리오 | 조건 | 기대 |
|---|---|---|
| D-1 동시 발송 | 전 사용자 × 3자산군 | 15분 이내 전건 `SENT` |
| provider 장애 | 전건 5s 타임아웃 | 재시도 3회 후 `FAILED`, 워커 생존 |
| provider 429 | rate limit | 백오프 후 회복, 중복 0건 |
| dispatch 2인스턴스 | 동시 pull | 중복 전송 0건 |
| 게이트 캐시 미스 | Redis 다운 | **요청 통과**, p95 영향 3ms 이내 |
| 등록 폭주 | 1대가 1분 60회 | rate limit 동작, p95 100ms 이내 |
| KMS 지연 | 500ms/호출 | 배치 복호화로 전체 시간 선형 증가 없음 |

## Acceptance Criteria

- [ ] **D-1 알림이 예정 시각 + 15분 이내에 발송된다**
- [ ] D-30/14/7/3이 + 2시간 이내다
- [ ] dispatch 워커가 1분 주기다
- [ ] **큐 적체 5분(12월 2분) 알람이 있다**
- [ ] 발송 지연 분포가 메트릭으로 수집된다
- [ ] **게이트 판정에 DB 조회가 없고 오버헤드가 3ms 이하다**
- [ ] **게이트가 fail-open이다**
- [ ] 헤더 없는 요청이 즉시 통과한다
- [ ] provider 호출이 배치 API다
- [ ] 전송이 트랜잭션 밖이고 동시성 상한이 있다
- [ ] **429에 백오프하고 즉시 재시도가 0건이다**
- [ ] dispatch가 다중 인스턴스에서 중복 전송 0건이다
- [ ] **D-Day 판정 워커가 쿼리 3회 이하고 N+1이 0건이다**
- [ ] INSERT가 한 번의 `createMany`다
- [ ] 워커 30초 초과 알람이 있다
- [ ] 워커 커넥션 합이 풀의 30% 이하다
- [ ] KMS 복호화가 배치로 일어난다
- [ ] KMS 실패가 워커를 죽이지 않는다
- [ ] **12월 전용 대시보드에 D-30/14/7/3/1 발송 완료가 표시된다**
- [ ] **D-Day 미발송 알람이 있다**
- [ ] 메트릭·로그에 토큰·금액이 0건이다
- [ ] 위 7개 부하 시나리오가 검증된다

## Open Questions

- 게이트가 fail-open이면 "낡은 앱이 잘못된 세금 계산을 보여주는" 상황을 못 막는다. **계산이 바뀌는 릴리스에 한해 fail-closed**로 전환하는 플래그가 필요한지.
- D-1 15분 SLO를 지키려면 12월에 dispatch 주기를 30초로 낮춰야 할 수 있다. 상시 30초로 둘지, 12월만 낮출지.
