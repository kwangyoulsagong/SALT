SALT 서버 MSA 전환 설계

Express · TypeScript 모놀리스를 도메인별 서비스로 나누고, 서비스는 Spring Boot · Kotlin으로 다시 쓴다. 한 번에 갈아엎지 않고 BFF 뒤에서 경로를 하나씩 옮긴다(스트랭글러). 새 도메인(저축 · 가계부 · 금융 팁)이 처음부터 Kotlin 서비스로 태어나고, 투자 쪽은 맨 뒤에 옮긴다.

결론

  1. 서비스 경계 = 도메인 경계. 프론트 도메인 패키지와 같은 이름으로 identity · savings · household · content · notification · portfolio · market · coach 8개. 예측(salt-forecast, Python)은 이미 분리된 9번째다.
  2. BFF는 그대로 Node로 둔다. 프론트가 보는 계약(뷰모델 · SSE · 시세 WebSocket)을 지키는 층이라, 뒤의 서비스가 TS에서 Kotlin으로 바뀌어도 프론트는 모른다. 이게 이전을 안전하게 만드는 장치다.
  3. 순서는 위험이 낮은 것부터. 신규 → 작은 기존 → 인증 → 투자. 가장 큰 coach(2.2만 줄)는 마지막이다.
  4. 배포 단위는 단계적으로 늘린다. 처음엔 Kotlin 멀티모듈 하나에 서비스 모듈을 담고(Spring Modulith로 경계 검증), 서비스를 프로세스로 쪼개는 건 각 단계에서 이유가 생길 때 한다. 코드 경계는 처음부터 MSA, 프로세스 경계는 필요에 따라.

상황방법예
화면이 여러 도메인을 모은다BFF가 각 서비스를 병렬로 부른다. 서비스끼리 서로 부르지 않는다홈 요약 카드 4장
한 도메인의 사건이 다른 도메인에 영향발행 서비스가 같은 트랜잭션에 아웃박스 행을 쓰고, 릴레이가 브로커로 보낸다. 받는 쪽은 멱등 처리household.ExpenseRecorded → savings가 "목표 지연 일수" 재계산
다른 도메인의 데이터를 자주 읽는다이벤트로 받아 자기 스키마에 읽기 전용 사본(프로젝션)을 둔다coach가 portfolio 보유를 프로젝션으로 가진다
지금 당장 답이 필요한 조회내부 REST 한 번 + 타임아웃 · 서킷 브레이커. 실패하면 degraded로 내린다(기존 응답 규약)coach가 market에 현재가 조회

첫 이벤트 목록

identity.UserRegistered          → savings · household · content (초기 상태), notification
savings.GoalCreated              → content (결혼 · 주거 목표 → 관련 제도 팁 트리거)
savings.GoalReached              → notification, content
household.ExpenseRecorded        → savings (지연 일수), content (고정비 증가 감지)

portfolio.TransactionRecorded    → coach (보유 프로젝션)

브로커는 RabbitMQ로 시작한다. 맥 한 대에서 돌리기 가볍고 Spring Modulith 이벤트 외부화가 지원한다. 이벤트 재생이 필요해지면(예: 프로젝션 재구성) Kafka로 옮긴다. 이벤트 스키마는 contracts/events/*.json에 두고 BFF · Python도 같은 정의를 읽는다.

데이터 소유권

  • 테이블 하나에 주인 하나. 이전 중에도 마찬가지다. 경로를 Kotlin으로 넘길 때 그 테이블의 DDL 주인도 Prisma에서 Flyway로 넘긴다.
  • 스키마로 먼저 가른다. identity · savings · household · content · market · portfolio · coach · notification · forecast. 서비스별 DB 계정은 자기 스키마만 쓴다. 다른 스키마를 조인하는 쿼리는 이벤트 · 프로젝션으로 바꾼다.
  • forecast가 public을 직접 읽는 4곳(가격 이력 · 휴장일 · 종목 마스터 · 판정 원장)은 market · coach가 내보내는 읽기 전용 뷰(market.v_daily_close_export 등)로 바꾼다. 테이블이 아니라 뷰가 계약이라는 ADR-004 원칙을 서버 쪽에도 똑같이 적용한다.
  • 금액은 BigDecimal. Prisma Decimal과 같은 정밀도(NUMERIC)를 유지하고, Shared Kernel의 Money VO를 Kotlin으로 옮긴다(value class + 통화).
  • 판정 원장 불변 트리거(UPDATE 차단)는 DB에 있으므로 언어와 무관하게 유지된다.

이전 단계 — 스트랭글러

매 단계가 같은 모양이다. ① 지금 응답을 골든 JSON으로 녹화 ② Kotlin 서비스 구현 ③ 같은 요청을 두 서버에 보내 응답을 비교(그림자 실행) ④ BFF 라우팅 스위치를 넘김 ⑤ 1주 지켜본 뒤 옛 코드 삭제. 되돌리기는 스위치 하나다.

S0

기반 · ADR-006

salt-platform/(Gradle 멀티모듈) · Docker Compose(Postgres · RabbitMQ) · identity JWKS를 위한 키 정리 · BFF에 경로별 라우팅 스위치 · 계약 테스트 하네스(BFF가 부르는 서버 API 전부를 골든 JSON으로). 하네스 규칙 salt-server/.claude/rules/**를 Kotlin판으로 새로 쓴다.

S1

savings · household — 새로 태어나는 도메인

기존 modules/goals(601줄)는 savings로 옮기고, 가계부는 처음부터 Kotlin. 옛 코드와 맞출 응답이 거의 없어 이전 위험이 가장 낮다. 이 단계에서 아웃박스 · 이벤트 · 스키마 권한 분리를 처음 증명한다.

S2

content · notification

금융 팁은 신규. notification은 587줄 · 이벤트 구독자로 바꾸기 좋은 첫 기존 컨텍스트.

S3

identity

토큰 발급자가 바뀌는 단계. 옛 비밀키 토큰과 새 JWKS 토큰을 일정 기간 둘 다 받는다(이중 검증). 초대 코드 시도 제한 · 감사 로그 그대로.

S4

portfolio

금액 계산 정확성이 핵심. 그림자 실행에서 평가금 · 평단을 소수점까지 비교한다.

S5

market + 수집 워커

KIS · 업비트 수집이 별도 프로세스(market-ingest)로 나간다. 국내 일봉이 멈추면 전망 카드가 꺼지는 의존(2026-10-09 · 10-20 사고)을 이 단계에서 끊는다 — 수집 프로세스가 API 서버와 따로 죽고 산다. forecast의 public 직접 읽기를 export 뷰로 바꾼다.

S6

coach

가장 크고(2.2만 줄) 규칙이 많다(근거 3종 렌더 게이트 · 판정 원장 불변 · 소유자 전용 전망 · 금지 표현 검증기). 유스케이스 33개를 묶음별로 나눠 옮긴다. 판정 엔진은 같은 입력에 같은 출력을 내는지 백테스트 스크립트로 전수 비교한다.

S7

Express 서버 종료

launchd com.salt.server를 내리고 Compose로 대체. 동면 모듈(mission · dashboard · feed)은 이전하지 않고 410 응답도 BFF로 옮긴 뒤 지운다.

비용과 위험

MSA의 운영 비용은 코드보다 운영에서 나온다. 지금은 한 사람이 맥 한 대에서 서버 하나를 돌린다. 서비스 8개 + 브로커 + 추적을 띄우면 로컬 개발도 Compose 없이는 안 된다. 그래서 S0~S2 동안은 서비스 모듈들을 한 프로세스(모듈러 모놀리스)로 띄우고, 프로세스 분리는 다음 신호가 있을 때 서비스 단위로 한다.

  • 분리 신호: 장애 격리가 필요하다(수집 워커 → S5에서 무조건), 확장 특성이 다르다(코치 LLM 대기), 배포 주기가 다르다(콘텐츠).
  • 이중 언어 기간: S1~S6 동안 TS와 Kotlin 서버가 같이 돈다. 규칙 · 훅 · 테스트를 두 벌 유지하는 기간을 줄이려고 한 단계가 끝나면 옛 코드를 바로 지운다.
  • 계약이 진실: BFF 골든 JSON이 이전의 합격 기준이다. 응답 필드 하나가 달라져도 프론트가 조용히 깨진다(PR 규칙 §5).
  • 제품 공통 수용 기준은 그대로: 주문 코드 경로 0 · 금액은 서버 · 근거 3종 · 확신 표현 0.

Open Questions

  • BFF도 Kotlin으로 옮길까. 지금 안은 유지(프론트 소유 · TS 타입 공유). Spring Cloud Gateway로 대체하면 뷰모델 조립을 어디서 할지가 다시 문제가 된다.
  • RN 앱 푸시(FEATURE-007)가 열리면 notification을 S2보다 먼저 프로세스로 분리할지.
  • 배포 환경. 자체 호스팅(FR-21) 위에 Compose로 갈지, 관리형 컨테이너로 갈지에 따라 S7 모양이 바뀐다.
