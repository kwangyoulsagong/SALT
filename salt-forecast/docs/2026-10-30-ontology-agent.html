SALT 예측 · 온톨로지 설계

FEATURE-008은 "데이터 파이프라인 → 온톨로지 → 에이전트"를 약속했다. 파이프라인과 예측 · 채점은 크게 만들어졌는데, 가운데 온톨로지와 끝의 에이전트가 비어 있다. 이 문서는 그 두 칸을 채우는 설계와, 예측을 투자 밖(저축 · 가계부)으로 넓히는 방법, MSA 안에서 예측 서비스의 위치를 정한다.

온톨로지가 비어 있어서 생기는 일. 뉴스(news_item) · 일정(scheduled_event) · 신호(signal_event) · 종목 마스터가 각자 테이블로 흩어져 있다. "이 뉴스가 어느 회사 · 어느 종목에 관한 것인가", "이 사건 뒤에 같은 업종이 어떻게 움직였나"를 묻는 쿼리가 매번 새로 짜인다. 에이전트가 쓸 도구도 그래서 못 만든다.

온톨로지 모델

ADR-004 결정대로 그래프 DB 없이 Postgres로 한다(2~3홉은 재귀 CTE). 모든 사실은 출처 · 관측 시각 · 수집 시각을 갖고, 시점 고정(as-of) 질의가 되도록 유효 구간을 둔다. 이게 누수 방지 규칙(time-and-leakage.md)과 같은 원칙이다.

forecast.entity
  id · kind · canonical_name · external_ids jsonb   -- kind: asset | company | person | institution | wallet | event | document | sector | policy
  created_at

forecast.relation                                    -- 엔티티 사이의 관계 (시점이 있는 간선)
  id · subject_id → entity · predicate · object_id → entity
  valid_from · valid_to                              -- 관계가 사실이었던 기간
  observed_at                                        -- 출처가 그 사실을 말한 시각
  ingested_at                                        -- 우리가 안 시각 (as-of 질의의 기준)
  source_url · source_kind · confidence
  -- predicate: issued · listed_as · holds · traded · mentions · affects · belongs_to · regulates

forecast.fact                                        -- 엔티티의 수치 · 속성 (시점이 있는 값)
  entity_id · attribute · value_num · value_text · unit
  valid_from · valid_to · observed_at · ingested_at · source_url

forecast.v_entity_asof(as_of timestamptz)            -- 계약 뷰: ingested_at <= as_of 만
forecast.v_neighbors(entity_id, depth, as_of)        -- 재귀 CTE, 최대 3홉

에이전트 — 숫자는 만들지 않는다

ADR-004 원칙 그대로: 숫자는 채점되는 통계 모델이 내고, LLM은 문장만 쓴다. 에이전트는 아래 도구만 쓸 수 있고, 도구 결과에 없는 숫자를 문장에 쓰면 검증기가 막는다.

도구돌려주는 것
get_forecast_card(asset, as_of)v_forecast_card — 구간 · 커버리지 · 기준 대비 · 빗나간 사례
get_neighbors(entity, depth≤3, as_of)관련 엔티티와 관계 + 출처 URL

get_documents(entity, since)언급 문서 제목 · 출처 · 시각
  • 검증기(이미 있는 것 재사용): 숫자 대조 · 금지어 · 명령형 · 인용(출처 URL 없는 주장 금지).
  • 개인 금액은 넣지 않는다. 보유 수량 · 평단 · 원화 손익은 프롬프트 밖. 화면이 서버 값을 직접 그린다.
  • 어디서 도나: 문장 생성은 요청 경로(서버 coach의 CoachExplainer 포트)에서, 도구는 forecast 스키마의 계약 뷰를 읽는다. 에이전트 때문에 Python 상시 서버를 띄우지 않는다.
  • 실패하면 템플릿. 지금 템플릿 해설이 기본값으로 남는다(FEATURE-008 FR-45).

예측을 투자 밖으로 — 개인 재무 전망

저축 · 가계부에도 "언제 / 얼마"를 묻는 화면이 생긴다. 이것도 예측이므로 투자 전망과 같은 규율로 다룬다: 한 점이 아니라 구간, 그리고 그 구간이 실제로 맞았는지 채점 이력을 같이 보여 준다(ADR-003 정신, 제품 공통 수용 기준 §6-4).

전망계산채점
목표 도달 구간사용자의 실제 적립 기록(월별 입금)의 경험 분위수로 "빠르면 ~ 늦으면" 날짜. 기록이 3개월 미만이면 구간 대신 "계획대로면 X월"만 보여 주고 이유를 쓴다3 · 6개월 전에 낸 구간에 실제 진척이 들어갔나
월말 지출 착지지금까지 지출 + 예정된 반복 지출 + 변동 지출 일평균 분포 × 남은 날지난달 같은 날짜에 낸 구간이 맞았나
목표 금액 실질가치물가지수(공식 CPI)로 "처음 정한 금액은 오늘 돈으로 얼마"계산값 — 채점 대상 아님, 기준일 표시
  • 계산은 도메인 서비스(savings · household)가 요청 시 한다. 사용자 데이터가 forecast 배치로 흘러가지 않게 한다.
  • 채점은 forecast가 한다. 서비스가 낸 구간을 이벤트(savings.ProjectionIssued)로 받아 forecast.personal_projection_score에 쌓고, 사용자 식별자는 해시로만 둔다. 커버리지(구간 안에 들어간 비율) 집계만 서비스로 돌려준다 — "이 계산기의 90% 구간은 지난 6개월간 실제로 87% 맞았다".
  • CPI 같은 공공 계열은 forecast의 ingest가 이미 하는 일(FRED · ECB와 같은 방식)이라 거기서 수집한다.

MSA 안에서의 위치

  • forecast는 이미 분리된 서비스다. Python 배치 · 상시 HTTP 없음 · 계약은 forecast 스키마 뷰. 이 모양을 유지한다.
  • DDL 주인을 옮긴다. 지금은 forecast DDL이 salt-server/prisma/migrations에 있다(ADR-004 §5). 서버가 Kotlin · Flyway로 가면, forecast 스키마 마이그레이션은 salt-forecast 안(plain SQL + 버전 표)으로 옮겨 "자기 스키마는 자기가"를 맞춘다. 뷰 계약이 바뀌면 소비자(coach)와 같은 PR 규칙은 그대로.
  • public 직접 읽기 4곳을 끊는다. price_history · market_holidays · kr_stock_master · judgment_ledger → market · coach가 내보내는 export 뷰로. 서버 설계 S5와 같은 시점.
  • 이벤트 구독: market.DailyCandleClosed를 받으면 해당 시장 일일 잡을 당긴다(지금은 cron 매시 확인). 놓친 회차 보정은 지금 로직 유지.

단계

O1

온톨로지 테이블 + 기존 데이터 적재

entity · relation · fact + as-of 뷰. 종목 마스터 · 뉴스 · 일정 · 신호 · 사건 반응으로 첫 그래프. 새 수집 없음. 누수 테스트: as-of 질의가 미래 ingested_at을 절대 돌려주지 않는다.

O2

엔티티 연결 품질

뉴스 → 종목 매칭 정밀도 · 재현율을 표본 200건 수기 라벨로 잰다. 기준을 넘기 전에는 에이전트 도구에 mentions를 쓰지 않는다.

O3

에이전트 도구 + 검증기 연결

도구 4종 · 블라인드 A/B 20건(템플릿 vs 에이전트). 이긴 경우만 소유자 전용으로 켠다.

O4

개인 재무 전망 채점

savings · household 서비스(서버 S1)와 같이. 채점 테이블 · 커버리지 집계 뷰.

O5

스키마 주인 이전 · public 읽기 제거

서버 S5와 같은 시점.

O6

DART 공시 · 내부자 (FC-REQ-002)

온톨로지가 서 있어야 의미가 있다. 그래서 O1 뒤.

Open Questions

  • 제도(policy) 엔티티를 forecast 온톨로지에 둘지, content 서비스에만 둘지. 같은 제도가 금융 팁 · 저축 계산기 · 투자(세금) 해설에 다 쓰여서 한 곳이 좋은데, 주인은 content가 맞다. 안: content가 원문 · 유효 구간의 주인, forecast는 이벤트로 받아 사본.
  • 개인 재무 채점에서 사용자 해시를 쓰는 것으로 충분한지(개인정보 처리 범위).
  • 에이전트 공급자 — 무료 Gemini는 입력이 학습에 쓰일 수 있어 개인 데이터가 없는 문장만 맡긴다(ADR-004 §4).
