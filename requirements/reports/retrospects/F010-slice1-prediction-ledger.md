# F010 슬라이스 1 — 예측 원장 + 규칙 IC — 회고

영역 회고: `salt-forecast/requirements/reports/retrospects/FC-REQ-008.md` · `salt-server/requirements/reports/retrospects/SRV-REQ-024.md` · `DB-REQ-017.md` · `DB-REQ-029.md`

- **이 슬라이스의 가장 큰 발견은 "단타 점수가 거꾸로 맞힌다"다.** 하루 3% 오른 종목에 +12 를 주는 규칙이 8년치 업비트 원화 시장에서 다음 날 수익률 순위와
  음의 상관(−0.038, CI 전체가 0 미만)이었다. 리서치는 "1주 방향 신호는 모멘텀 1~4주"라 했지만 이 시장의 단기는 반전이 더 강했다(도전자 `mom_28d` 도 음수).
  **문헌의 결론을 이 시장에 옮기기 전에 이 시장으로 잰다** — 사전등록이 없었다면 이 결과를 보고 "모멘텀을 더 넣자"로 갈 뻔했다
- 사용자 요청 "고래를 늘려라 · 더 긴 데이터"가 두 갈래(가중 vs 데이터)로 읽혀 한 번 물었다. 답이 "IC 뒤 가중 · 1년"으로 좁혀져 용량 결정(수백 GB → 1년 25분)이 바로 됐다.
  **그리고 결과는 가중 0 이다** — 요청과 반대 방향의 결론을 사용자에게 그대로 전하는 것이 이 슬라이스의 몫이다
- 고래 데이터가 적었던 진짜 원인(화면 호출 때만 저장)은 `count(*)` 한 줄이 찾았다. 슬라이스 0 회고의 "성적 · 판단 슬라이스는 `SELECT count(*)` 부터"가 두 번째로 맞았다
- 실 DB 첫 실행이 결함 넷을 드러냈다 — 사전등록 JSON 날짜 · `rule_ic` CHECK · 불변 트리거 `OLD.id` · 대형 체결 재개 지점. 넷 다 단위 테스트는 통과하고 있었다.
  **DDL 과 워커는 실제 DB 에서 두 번 연속 돌리기 전까지 끝난 것이 아니다**
- 커밋을 되돌리기 단위로 나누다 `composition.ts` 한 파일에 두 커밋의 배선이 섞였다. 부분 스테이징을 패치로 했는데 확인 없이 stash 를 쳐서 한 번 멈췄다 —
  다음엔 배선을 먼저 나눠 쓰거나 한 커밋으로 둔다

## Action

- `mode-decision@2` 결정을 받으면: 스냅샷 · 원장에 규칙 버전 필터 → 부호 반전 · 가중 0 → 반전 항목 근거 문장 → `rule_items.py` 버전 분기
- 2026-11-23 라이브 IC 첫 실행(원장 × 일봉 종가, `source = live`)
- 슬라이스 2(국면 · 변동성)에서 삼중 장벽을 σ 손절 · 익절과 같이 재설정

## 판정 반영 (`mode-decision@2`, 2026-09-28~29)

- 가중을 빼자 **후보 문턱(70)에 닿을 수 없게 됐다** — 특성화 테스트 값을 다시 쓰다 발견했다. 문턱을 비율로 옮기는 "보기 좋은" 해법이 있었지만
  표본 안에서 재 보니 그 후보 칸은 시장 대비 초과 수익이 0 이었다. **후보를 되살리는 것보다 근거 없는 후보를 안 띄우는 쪽이 사용자 돈에 맞다.**
  대신 "피하기"가 실제로 덜 오른 종목을 골랐다는 것이 이 규칙의 쓸모다
- 점수에서 뺀 항목이 **해설 LLM 사실 목록에는 남아 있었다.** 규칙 한 곳(`SCORED_ITEMS`)이 점수 · 문장 · 해설을 같이 정하게 했다 — 규칙을 바꿀 때 근거가 새는 경로는 점수 함수 밖에도 있다
- 규칙 버전 열이 없었으면 v2 표본이 v1 성적표에 섞였다. 원장에는 처음부터 버전을 넣었지만 기존 스냅샷 표에는 없었다 — **채점되는 모든 행에 만든 규칙의 버전**

### Action

- `rule-ic@2` 사전등록(라이브 IC 뒤): 문턱 · 단타 1시간 RSI · 업비트 고래 원문
- 슬라이스 5 목표 비중 부족분 매수 제안 — 지금 규칙으로는 후보가 없다
