## 판단 — 리뷰가 볼 곳

1. **S1f = 분류 표를 건드리는 둘** — 통장 쪼개기(FEATURE-013 FR-6 Must)와 사용자 분류는 둘 다 "어느 봉투에 드나"를 바꾼다. 사람 장부 · 이야기 카드는 새 원장 · 집계, 리볼빙은 "2025년 이후 규정 원문 대조"(FEATURE-013 미결)가 먼저 — S1g **정정 2026-11-05** S1g 는 이야기 카드만 닫았고 사람 장부 · 리볼빙은 S1h(`MONEY-S1g-household-story-slice.md`).
2. **내 분류 키는 같은 열 · 난수 키 · 지우기는 보관** — V1 이 `expense.category` 에 CHECK 를 두지 않은 이유가 이것이다. 키는 `u_` + 12자리 난수(이름이 아니라 — 이름을 바꿔도 지난 지출이 따라온다 · 경로 조각이 늘 ASCII). 지우면 고르는 칸에서만 빠지고 지난 지출 · 봉투 · 템플릿은 이름 그대로(보관 행이 남는다). 묶음(needs · wants)은 사용자가 고르고, 바꾸면 이번 달 50/30/20 봉투도 따라 옮긴다(키가 같다)
3. **통장 쪼개기 = 이름표 넷 · 템플릿이 가른다** — 급여(월급이 들어오고 자동이체가 나가는 곳) · 생활비 · 저축 · 비상금. **반복 템플릿으로 적은 지출 = 급여 통장(고정비), 나머지 = 생활비 통장** — 분류로 가르지 않아 내 분류와 엮이지 않고, 고정비 찾기(S1e)의 "매달 적기로"가 그대로 급여 통장으로 간다. 급여 통장 몫 = 소득 − 생활비 · 저축 · 비상금(저장 안 함). 셋의 합이 소득을 넘으면 400 — 지출 초과가 아니라 입력이 틀린 것(지출은 여전히 막지 않는다). 저축 · 비상금은 지출이 들지 않는 칸(50/30/20 의 모으기 몫과 같은 자리) · 0 이면 빈 칸. 통장과 잇는 것 0
4. **분류 표 한 곳(`CategoryBook`)** — 묶음 · 고를 수 있는지 · 순서를 지출 · 봉투 · 템플릿 · 제안 · 화면이 같은 답으로 쓴다. 넣기는 `INSERT … SELECT … WHERE (보관 안 한 수) < 20 ON CONFLICT DO NOTHING` 한 문장(같은 이름은 부분 유일 인덱스 `lower(name) WHERE archived_at IS NULL`). 못 넣었으면 그 **뒤에** 한 번 읽어 까닭을 가른다(409 `CATEGORY_TOO_MANY` · `CATEGORY_NAME_TAKEN`) — 오류 코드로 가르지 않는다. 상한은 느슨하다(동시 두 번이면 21 — 칩 줄 길이를 지키는 값이지 불변식이 아니다)
5. **쿼리 수 — 흔한 길은 그대로** — 월 화면 21 → 22(분류 표). 저장 · 홈은 기본 분류 · 봉투 방식이면 그대로(내 분류 꼴 키를 적거나 50/30/20 일 때만 +1). 월 합 한 문장이 (분류, 정밀도, 템플릿인가)로 묶어 급여 통장 몫을 같이 낸다(상수는 `inline` — 바인드 변수면 SELECT · GROUP BY 식이 달라 Postgres 가 거절)
6. **화면 이름은 한 곳(`useCategoryLabel`)** — 기본 분류는 프론트 문구, 내 분류는 서버 이름. 월 화면은 이미 받은 `month.categories` 를 넣어 **서버 HTML 부터** 이름이 맞고(수화 갈림 0), 다른 화면은 분류 표 조회 하나를 같이 쓴다. 칩은 표를 받기 전에도 기본 12 를 바로 그린다
