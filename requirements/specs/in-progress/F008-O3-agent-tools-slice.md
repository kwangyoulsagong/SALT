## Summary

사용자 "새 브랜치 파고 다음 파이프라인 진행" — §4-1 3a "예측 바탕" 줄의 남은 칸 `FC-REQ-023`(O3). 브랜치 `feat/fc-req-023-agent-tools`.

한 줄 — **에이전트는 고르기만 한다.** 모델이 도구(전망 카드 · 이웃 · 사건 반응 · 문서)와 대상을 JSON 으로 고르면 서버가 예측 계약을 부르고,

## 판단 — 리뷰가 볼 곳

1. **도구 호출을 모델에게 주지 않고 "고른 목록"만 받는다** — 로컬 CLI 는 도구 0 · 빈 폴더 격리(`ddd-infrastructure.md` §6)가 이미 규칙이다. 모델이 DB 를 직접 부르게 하는 대신
   서버가 대상(이 종목 + 앞 결과 이웃) · 사건 종류(메뉴)를 검사하고 부른다. 왕복 ≤ 2 · 호출 ≤ 4. Spring AI 도구 호출은 S6 Kotlin 이전 때 다시 본다
2. **검증기를 새로 만들지 않는다** — 도구 줄이 해설 입력 `tools` 한 칸으로 들어가 허용 숫자 · 인용 사실표가 된다(제목 줄 숫자는 기사처럼 뉴스 칸만)
3. **스펙 정정 셋** — 뷰는 인자를 못 받아 함수 · 반응 인자 `(event_kind, sector)` → `(event_kind, 종목 · 시장)`(채점된 업종 통계 0 — 지어내지 않는다) ·
   출처 URL 은 원천에 있을 때만(온톨로지 관계 행 주소 0건, DART 는 접수번호로 만든다)
4. **"최근"은 일어난 시각, 누수 거르기는 알게 된 시각** — 2016~ 공시를 백필해 알게 된 시각이 전부 백필한 날이라 1년 전 공시가 이번 주 공시로 나왔다
5. **반응 도구는 최근 이 종목에 실제로 일어난 사건만** — 1회차 A/B ② 에서 평가자 셋이 같은 이유("오늘 없는 사건의 과거 통계")로 운영 해설을 골랐다(3 : 17). 규칙 + 시험으로 고친 2회차 14 : 5
6. **켜기는 사용자 판정** — REQ 문턱(템플릿 대비 20 : 0)과 더한 문턱(운영 해설 대비 14 : 5)을 넘었지만 도구 인용이 20건 중 2건이라 승리 원인이 도구라는 증거가 약하다. 켜면 소유자 해설마다 LLM 1회 더(고르기) · 소유자 해설 갈래가 필요하다

- 평가 방식: 독립 평가자 opus · sonnet · haiku, 평가지만 복사해 넘김(키 · 저장소 접근 0), 다수결. 평가 표 `*.ratings.json` · 집계 `npm run explain:agent-ab -- --score <평가지> <ratings>`
- 1회차 ② 공통 지적(셋 다): 오늘 일어나지 않은 사건의 과거 반응 통계(실적 공시 · 김치 프리미엄 뒤 오른 비율) · 같은 업종 종목 나열 = 군더더기 → 규칙으로 고침(최근 실제 사건만 · 같이 언급 3건 이상만 · 무관하면 부르지 않음)
- **2회차 해석 주의**: 도구 사실이 문장에 인용된 해설 20건 중 2건(`-r2-trace.json` `toolCited`). 이긴 14건 대부분이 도구 인용 0 — 승리가 도구 덕인지, 같이 바뀐 작성 프롬프트 한 줄("판단 근거 · 원인을 빼고 도구 사실로 채우지 않기")과 생성 편차 덕인지 이 실험으로는 못 가른다
- 사실 오류 지적(양쪽 공통으로 나온 것): 코인 코드 이름(XRP) · "평소 범위 안이라 소식이 없다" 인과 뒤집기 · 24시간 코인에 "마감" · 내부 문구("이 판단에 규칙이 적은 주의 사항은 없습니다") 노출 — 에이전트만의 결함이 아니라 지금 작성기 공통

## 같은 원인 고침

- 기존 `f_neighbors`(FC-REQ-022) 3홉 p95 가 데이터 증가로 2.4초(코스피 시작 69초)라 시험이 깨져 있었다 — 에이전트 이웃 함수에서 찾은 원인과 같다. `20261118200100` — 결과 같음(EXCEPT 양방향 0) · p95 33ms
